# DST Manager 插件式扩展平台功能需求与要求书

## 1. 文档定位

本文定义 DST Manager 在基础编辑能力稳定后的长期可扩展方向，回答“用户需要哪些扩展能力、宿主必须守住哪些边界、怎样判断扩展真正可用”。本文不规定类名、数据库表、进程协议、模块目录或实施顺序；这些内容应在对应 Spec、Architecture、ADR 和 Plan 中分别确定。

本文中的“扩展”是 DST Manager 的产品扩展，不等同于 `plugins/src/DstManager.AutoCAD/` 下的 AutoCAD Worker Plugin。后者是受控 CAD 数据库操作适配器，继续服从现有 Core Console、安全脚本和版本匹配规则。

## 2. 已确认的方向

本需求基于以下已确认决策：

1. 采用分层扩展路线（即“插件式扩展平台”）：简单能力可作为宿主内置扩展运行，受控 AutoCAD 作业通过既有 CAD 任务边界运行，业务连接器和完整工程通过独立进程或 sidecar 集成。
2. 扩展以项目维护者或组织内部开发、审核后发布的受信扩展为主。
3. 首期扩展平台的扩展随主程序打包交付，只支持启用和停用，不开放未知来源扩展包安装、在线市场或自动下载。
4. 扩展不得直接修改正式 DST、DWG 或宿主数据库。涉及工程变更时，扩展只能提交结构化 `Change Proposal`，由宿主完成预览、基准修订校验、CAD 执行、结果验证、发布和回滚。
5. 只产生新成果的功能通过 `Artifact` 流程交付，不伪装成工程修订。
6. 借鉴 [Cordis](https://github.com/cordiverse/cordis) 的 Context、Service、依赖声明、生命周期和副作用清理理念，但不把 Cordis 直接引入 Python 安全内核。未来如建立 TypeScript sidecar，可在该 sidecar 内部重新评估 Cordis。

总体原则为：

> 一切外围能力皆可扩展，一切安全不变量属于宿主；一切能力皆可组合，但不是一切能力皆可替换。

## 3. 背景

DST Manager 已具备工作区打开、DST/AcSm 投影、受控编辑、草稿、完整预览、CAD Worker、永久修订、整批发布和恢复能力。图纸页、属性页和配置页完成后，新增业务价值将更多来自已有基础能力的组合，例如：

- 导出图纸目录和工程报告；
- 打包、校验并传递项目成果；
- 通过 AutoCAD Core Console 执行随包审核的打印、归档等受控 CAD 作业；
- 连接业务平台并同步项目元数据；
- 嵌入已有完整前后端工程，例如 DWG 查看或编辑应用；
- 以统一方式增加 AutoCAD 版本与运行能力。

若继续把这些功能直接追加到 `DstManagerService`、FastAPI 路由和固定标签栏，会逐渐形成新的耦合：扩展无法独立启停、依赖关系不可见、故障影响宿主、界面入口持续膨胀，并可能绕过已经建立的工程安全边界。

## 4. 目标用户

### 4.1 主要用户

- 使用 DST Manager 管理真实 DST/DWG 工程的单机用户；
- 为固定业务流程制作内部扩展的项目维护者；
- 负责成果移交、目录导出和平台数据同步的工程人员。

### 4.2 次要用户

- 提供 DWG 查看、编辑或专业处理能力的内部系统开发者；
- 负责新增 AutoCAD 版本适配和运行环境维护的技术人员。

首期扩展平台不面向公开第三方扩展作者，也不向最终用户承诺运行未知来源代码的安全性。

## 5. 要解决的问题

1. 新功能目前只能作为宿主固有功能接入，不能可靠启停或独立诊断。
2. 各功能容易直接依赖内部服务、数据库和文件路径，缺少稳定的能力边界。
3. 导出成果、工程变更、网络同步和完整应用嵌入的风险等级不同，不能共用一种无差别的运行方式。
4. 扩展故障、依赖缺失或配置错误不应阻止用户打开工作区或使用核心编辑能力。
5. 用户需要知道扩展来自哪里、具有什么能力、为何不可用、正在执行什么任务，以及结果保存在哪里。
6. 动态页面和操作入口必须延续现有桌面界面的信息层级、主题、键盘模型和真实环境验收要求，不能因“插件自带界面”形成互相冲突的产品体验。

## 6. 目标

### 6.1 产品目标

- 在不改变 DST/DWG 安全内核的前提下，让可选业务能力能够被发现、配置、启用、停用和诊断。
- 允许不同风险和技术栈的扩展选择宿主同进程、受控 CAD 任务、独立进程或 sidecar 运行方式。
- 让扩展通过最小、可审计的宿主能力完成工作，不依赖宿主内部实现。
- 统一表示扩展产生的成果、候选变更、任务、日志和错误。
- 保证扩展缺失、禁用、失败或不兼容时，核心工作区仍可安全使用。
- 为未来增加业务连接器、嵌入式工程和 AutoCAD 版本适配保留稳定演进路径。

### 6.2 可观察的成功结果

- 停用任一非核心扩展后，应用仍能启动、打开工作区并完成既有核心流程。
- 一个只读扩展无需直接访问数据库或正式工程写入接口，即可读取带修订身份的工作区快照并生成可追踪成果。
- 一个提出工程修改的扩展无法绕过现有预览、确认、锁、CAD、验证、发布和回滚链路。
- 扩展启动失败不会造成宿主白屏、核心 API 启动失败或发布恢复被跳过。
- 用户可以在统一界面中辨认扩展状态、权限、配置、任务和结果，并能从错误中恢复。
- 新增扩展页面在浅色、深色、最小支持视口、200% 缩放和键盘操作下保持可用。

## 7. 非目标

- 首期扩展平台不提供第三方扩展市场、在线安装、自动下载、依赖自动解析或数字签名体系。
- 不提供通用脚本、Shell、命令行或任意 AutoCAD 自动化运行器，也不把进程隔离宣传为恶意代码沙箱。
- 不把领域模型、修订基准、文件锁、发布器、恢复器、持久任务或权限代理改造成可替换插件。
- 首期不提供扩展间直接互调 API；扩展组合仅通过宿主能力、`Change Proposal` 与 `Artifact` 中介实现。
- 不迁移 Python/FastAPI 控制面到 Node.js，不以 Cordis 重写宿主。
- 不允许用户或普通扩展提交任意 Shell、SCR、AutoLISP、.NET 程序集路径或 AutoCAD 命令；受控 CAD 作业只能调用随包登记并审核的固定实现。
- 不允许扩展任意替换桌面壳、全局导航、全局样式或核心确认流程。
- 不在一个版本中一次性交付目录导出、打包、受控 CAD 作业、连接器和嵌入应用的全部能力。
- 不因扩展平台引入多用户、远程 Worker、云端控制面或后台无人值守同步；这些能力需要另行立项。

## 8. 核心与扩展边界

### 8.1 永久属于宿主内核的能力

- 工作区身份、根目录和路径边界；
- DST 解码、AcSm DOM、领域投影和确定性规则；
- 当前修订、文件身份和基准漂移判断；
- `Change Proposal` 的校验和预览；
- CAD 能力授权、任务预算和 Worker 调度；
- 正式文件锁、暂存、验证、发布日志、永久 before 快照和恢复；
- 持久任务状态、审计和错误码治理；
- 凭据代理、扩展权限裁决和扩展注册表；
- 宿主启动、数据库迁移和发布恢复顺序。

这些能力可以提供受限接口，但扩展不能替换其最终裁决。

### 8.2 允许扩展的能力

- 只读检查、统计、报告和图纸目录导出；
- 成果收集、校验、压缩、manifest 和校验和生成；
- 用户明确触发的打印、归档等受控 AutoCAD 作业；
- 外部业务平台连接、字段映射和同步建议；
- 工作区页面、工具栏动作、对象上下文动作、设置分区、任务详情和 Artifact 预览；
- DWG 查看、编辑或专业处理工程的 sidecar 适配；
- 经宿主认可的 AutoCAD 运行时能力提供者。

## 9. 扩展类型

| 类型 | 典型用途 | 默认运行边界 | 允许的主要输出 |
| --- | --- | --- | --- |
| 内置扩展 | 图纸目录、报告、成果打包 | 宿主同进程，受限能力注入 | `Artifact`、只读诊断、`Change Proposal` |
| 受控 AutoCAD 作业扩展 | 打印 PDF、生成脱离管理的归档副本 | 既有 CAD 任务边界、任务暂存目录和匹配版本的 Core Console | `Artifact`、执行报告和日志；不得输出 `Change Proposal` |
| 连接器扩展 | 业务平台元数据同步 | sidecar 或独立进程，经凭据与网络代理 | 同步差异、审计、`Change Proposal` |
| 嵌入应用适配器 | DWG 查看/编辑等完整工程 | 独立服务和隔离页面 | 候选成果、候选文件、`Change Proposal` |
| 特权运行时提供者 | AutoCAD 版本与命令能力 | 宿主审核并随包交付 | 受控 CAD 能力，不直接面向普通扩展 |

同一扩展不得因为启用了更多权限而在运行中静默改变类型。需要更高权限或新的运行方式时，必须更新声明并重新经过产品和安全评审。

## 10. 功能需求

### EXT-001：扩展清单与发现

- 每个扩展必须具有稳定且全局唯一的 `extension_id`、名称、版本、说明、来源、扩展类型和默认启用状态。
- 扩展必须声明兼容的宿主契约版本、必需与可选能力、设置项、权限和 UI 贡献点。
- 首期扩展平台只发现随主程序打包且已登记的扩展，不扫描任意用户目录，不从网络下载代码。
- 清单缺失、重复、无效或不兼容时，该扩展不得激活；错误必须可见且不得阻止其他扩展和核心宿主启动。
- AutoCAD Worker Plugin 必须使用独立类别和文案展示，不能与普通业务扩展混为一谈。

### EXT-002：启用、停用与生命周期

- 用户能够在配置页面查看并启用或停用非核心扩展；不可停用的宿主内核不得伪装成扩展列表项。
- 扩展至少具有：已发现、已停用、等待依赖、启动中、可用、停用中、已停止、失败、不兼容等可区分状态；其中“停用中”在仍有安全任务进行时对用户显示为“停用待任务完成”。
- 必需能力缺失时扩展进入等待依赖或不可用状态，不得用空对象或默认值假装成功。
- 扩展启用状态跨应用重启保留；宿主升级后必须重新检查兼容性。
- 停用时先禁止新任务和新入口。已有安全任务进入可证明安全的终态后再卸载；处于发布或恢复阶段的任务不得被插件生命周期强行中断。
- 扩展注册的路由、菜单、监听器、计时器、临时资源和 sidecar 进程必须归属于其生命周期，并在停用时按确定顺序清理。
- 清理失败必须产生诊断，不能把仍在运行或仍占用资源的扩展显示为“已停用”。

### EXT-003：能力声明与最小授权

- “能力（Capability）”指扩展可调用的功能面，决定扩展能否激活与是否降级；“权限（Permission）”指对数据与操作的具体授权，按工作区、任务与扩展身份作用域化。两者均须在清单声明并经宿主裁决。
- 扩展只能取得清单已声明、宿主已允许且当前可用的能力。
- 宿主应按工作区、任务和扩展身份提供作用域化能力，避免扩展持有永久全局对象。
- 必需能力决定能否激活；可选能力缺失时扩展可以降级，但必须在界面说明缺少的功能。
- 扩展不得取得完整应用服务、数据库会话、AcSm 可写 DOM、发布器或未经约束的正式文件路径。
- 能力调用必须能够关联 `extension_id`、工作区、任务和操作日志。

### EXT-004：只读工作区快照

- 宿主向扩展提供不可变、可序列化且带 `workspace_id`、`revision_id` 的工作区快照。
- 快照只包含扩展声明所需的最小数据；路径、诊断和敏感字段按能力裁剪。
- 获取快照不得创建 `.dst-manager/`、改变 DST/DWG 或更新时间戳。
- 长任务在提交结果时必须再次核对快照修订；发生漂移时结果应标记过期并要求重新生成或重新预览。

### EXT-005：候选变更 `Change Proposal`

- 扩展提出的工程变更必须是结构化、可校验、带来源扩展和基准修订的候选变更。
- 用户必须在宿主统一预览中看到业务变化、受影响文件、是否需要 CAD、风险和扩展来源。
- 候选变更只能由宿主转换为既有受控命令或后续正式定义的新命令；扩展不得提交任意 XML、SCR、Shell 文本或文件覆盖指令。
- 基准漂移、能力变化、扩展停用或输入变化必须使旧 Proposal 失效。
- Proposal 被拒绝、验证失败或发布失败时，扩展输入和诊断应保留，但正式工程保持发布前状态。

### EXT-006：成果 `Artifact`

- 目录表、报告、PDF、派生 DWG、归档包、ZIP、manifest、校验和、缩略图和交换文件统一登记为 `Artifact`。
- Artifact 必须记录来源扩展、来源工作区与修订、类型、创建时间、状态、文件哈希、管理关系和可读说明。
- 保留 DST 管理语义的成果与已经解除 DST 关联的归档成果必须可区分；后者标记为 `detached`，不得作为可重新打开或回写的 DST Manager 工作区成果展示。
- 生成过程只写宿主分配的暂存或输出目录，完成并校验后才向用户展示可导出结果。
- Artifact 创建不自动成为工程修订；只有正式工程文件发生受控变化时才进入修订链路。
- 删除、覆盖、重新生成或导出 Artifact 时必须明确目标，不得通过未验证的文件名逃逸到允许目录之外。

### EXT-007：扩展任务

- 耗时扩展工作必须进入统一任务模型，显示扩展来源、阶段、进度、开始/结束时间、结果和错误。
- 扩展任务状态应持久化；应用重启后能够区分可恢复、可重试、已中断和需要人工检查的任务。
- 用户取消只在扩展声明并实现安全取消时可用；发布和恢复阶段沿用宿主不可随意取消的约束。
- 单个扩展失败不得使其他扩展任务或 CAD 发布任务失去状态所有权。
- 日志必须去除凭据和敏感路径，并保留足够的扩展版本、输入摘要和错误码用于排障。

### EXT-008：受控 AutoCAD 作业扩展

- 本能力只用于通过 `accoreconsole` 执行打印、归档等预定义 AutoCAD 作业，不提供 Shell、Python、通用命令行或用户自定义脚本能力。
- 受控 AutoCAD 作业扩展属于随主程序打包、由项目维护者审核的内部特权扩展；最终用户只能启用、停用、选择作业和填写结构化参数，不能提供 `.scr`、`.lsp`、`.dll`、命令序列或可执行文件路径。
- 每个作业必须以稳定 `operation_id` 登记用途、参数 Schema、支持的 AutoCAD 版本、固定 SCR 渲染器、允许调用的随包 `.NET` Worker 或 AutoLISP `.lsp`、超时、输入范围、预期 Artifact 和验证规则。
- 随包 AutoLISP 脚本属于新增脚本执行面；在完成独立的脚本安全设计与评估前，不得将 AutoLISP 纳入随包交付与作业登记。
- 作业沿用现有 CAD 能力选择、固定 SCR、安全参数渲染、匹配版本 Worker、任务预算、日志和 Core Console 进程托管规则；不得把用户输入直接拼接为 SCR、AutoLISP、Shell 命令或文件操作指令。
- 宿主只向作业提供只读工作区快照以及复制到任务暂存目录的输入文件；`accoreconsole`、SCR、Worker 和 AutoLISP 只能读写该任务目录及宿主明确分配的输出目录。
- EXT-008 严格采用 Artifact-only 模型：作业永远不得提交 `Change Proposal`，不得调用正式发布器，不得覆盖、替换或回写工作区中的 DST/DWG，也不得把派生 DWG 伪装为当前工作区修订。
- 打印等非归档作业不得改变输入副本；宿主应在执行前后校验文件身份或哈希，并将意外修改判定为失败。输出 PDF、日志和报告经校验后登记为 Artifact。
- 生成 DWG 的普通派生作业只能修改明确允许的非布局、非 DST 关联内容；执行后必须校验布局集合、布局名称与顺序、关键身份以及 DST/AcSm 关联等受保护不变量，发现越界变化时不得登记成功 Artifact。
- 归档作业是显式例外：只能修改归档副本，可以按作业声明将字段转为普通文本、绑定外部参照并解除 DST 关联；结果必须标记为 `detached` Artifact，并在界面明确说明不能再作为 DST Manager 工作区打开或回写。
- 作业必须支持超时、受控终止、日志捕获、遗留进程检测、部分输出隔离和失败清理；仅完成且通过声明验证的文件可以登记为成功 Artifact。
- 将来如需正式修改源 DWG，必须另立能力类型和安全设计，不得扩张 EXT-008 的权限。

### EXT-009：成果打包与传递

- 用户能够基于明确修订选择受控成果范围，查看将包含、排除和缺失的文件。
- 打包结果至少包含文件清单、相对路径、哈希、来源修订、生成时间和扩展版本。
- 正式打包前应检查缺失引用、同名冲突、路径越界、空间不足和执行中工程变更。
- 打包失败不得留下被界面误认为完整的成果；成功结果登记为 Artifact。
- 是否包含修订快照、日志、外部参照或敏感诊断必须由独立选项和明确说明控制。

### EXT-010：业务平台连接器

- 连接器必须明确平台身份、同步方向、字段映射、触发方式和支持的数据范围。
- 连接器的首个交付阶段由用户主动触发同步，不默认后台轮询或无人值守写入。
- 凭据由宿主凭据代理保存和提供，不进入扩展清单、普通设置、工程目录、日志或 Artifact。
- 拉取或推送前必须展示差异、冲突、跳过项和远端不可用状态。
- 远端变化映射为 Change Proposal；本地变化推送时必须绑定确定修订并支持幂等识别。
- 网络超时、认证失效、部分成功和远端限流必须具有明确状态和安全重试语义。

### EXT-011：完整工程与嵌入应用

- 已有完整前后端工程以 sidecar 和受限 UI 容器接入，不要求迁入宿主源码或共享内部状态管理。
- sidecar 必须完成版本握手、健康检查、扩展身份确认和受限会话建立；失败时宿主核心页面保持可用。
- 嵌入页面只能通过版本化桥接协议请求宿主能力，不直接访问宿主数据库、Python 对象或任意本地路径。
- 查看型应用使用只读副本或受控读取能力；编辑型应用操作宿主提供的暂存副本，完成后返回候选文件、哈希和 Change Proposal。
- 候选 DWG 发布必须继续经过文件基准、匹配 CAD 能力、验证和整批发布，不以 sidecar 的“保存成功”代替宿主成功。
- 嵌入应用的崩溃、刷新、升级或关闭不能使正式工程保持未知写入状态。

### EXT-012：AutoCAD 运行时能力扩展

- 新增 AutoCAD 版本时，应能够登记版本、Core Console、Worker Plugin、DWG 兼容范围、命令能力和健康状态。
- AutoCAD 运行时提供者属于随包审核的特权适配器，不向普通扩展开放任意命令注册。
- 任务必须根据所需能力而非仅凭年份选择可用运行时；最终选择和兼容性校验由宿主完成。
- 运行时缺失、不匹配或能力不足时，扩展必须在执行前得到明确诊断，不得静默选择其他版本。
- 既有 2016/2020 行为、固定 SCR、单任务版本选择和真实系统测试门禁继续有效。

### EXT-013：设置、数据与升级

- 扩展设置按 `extension_id` 隔离，并与应用设置、工作区偏好、CAD 运行时配置和凭据分区展示。
- 设置必须有版本和校验规则；无效设置阻止对应扩展激活，但不阻止宿主启动。
- 扩展升级必须保留或显式迁移兼容设置；迁移失败时保留旧数据和可恢复信息。
- 扩展不得自行修改宿主数据库 Schema。确需宿主持久化的新公共概念必须经过正式迁移和架构评审。
- 停用扩展默认保留其设置和历史 Artifact；清除数据必须是独立、明确且可说明影响的操作。

### EXT-014：兼容性与发布

- 扩展必须声明宿主契约版本和自身版本；不兼容扩展不能进入活动状态。
- 扩展版本跟随现有 SemVer、rc 预发布、GitHub Releases 和可追溯构建规则。
- 首期扩展平台的扩展与主程序作为同一绿色包构建、测试和发布；不得在目标机器临时下载缺失代码。
- 发布包必须能够列出所含扩展及版本，诊断信息能够确认实际加载版本。
- 宿主升级、降级和 rc 验证必须覆盖扩展启停状态、设置兼容、Artifact 可读性和核心回归。

## 11. 前端功能与体验要求

扩展平台涉及配置页、动态导航、任务浮层、Artifact 结果和可能的嵌入页面，属于 [GUIDE-DM-001](../../guides/GUIDE-DM-001-frontend-design-implementation-gates.md) 定义的 L 级跨域改动。整体必须拆成可独立演示、实施和验收的子项目；每个子项目均执行 G0～G9，不得用本文直接替代 Spec、Demo、设计冻结、技术映射或 Plan。

### UI-001：扩展中心

- 配置页提供统一扩展中心，展示名称、说明、版本、来源、类型、状态和启停入口。
- 用户可以查看必需/可选能力、权限、设置、最近错误、活动任务和产生的 Artifact。
- “已停用”“等待依赖”“失败”“不兼容”“停用待任务完成”必须以文字和视觉共同表达，不只依赖颜色。
- 错误应说明用户能够执行的恢复动作，例如补充配置、完成当前任务、重新启动或查看诊断。
- 核心内核、AutoCAD Worker Plugin 与普通业务扩展使用不同分组和说明，避免误停用安全基础。

### UI-002：受控贡献点

- 宿主只开放预定义贡献点：工作区页面、工具栏动作、对象上下文动作、设置分区、任务详情和 Artifact 预览。
- 扩展不能替换核心图纸、属性、修订页面，不能覆盖全局快捷键、确认流程或错误处理。
- 扩展入口必须由宿主根据状态和能力统一生成，不能由扩展任意修改导航 DOM。
- 导航顺序、分组、名称冲突和入口数量必须有确定规则；扩展较多时仍能搜索和定位。
- 停用扩展后，其入口和动作应完整消失；若用户正位于该扩展页面，宿主先处理未保存输入和安全任务，再返回稳定核心页面并恢复焦点。

### UI-003：一致的视觉语言

- 内置扩展必须使用宿主设计令牌、基础组件、图标规则、间距、焦点样式和浅深主题。
- 扩展样式必须限定作用域，不得通过全局选择器改变核心页面、任务浮层或 ActionDock。
- 不允许用“插件自带风格”为理由跳过信息层级、可访问性和响应式要求。
- 独立嵌入应用可以保留自身品牌，但宿主边框、标题、状态、关闭/返回和权限提示必须一致。

### UI-004：状态与恢复

- 扩展中心及扩展页面至少覆盖初始、加载、成功、空数据、部分数据、失败、重试、能力缺失和不兼容状态。
- 涉及输入时必须区分未修改、编辑中、校验失败、未提交、任务处理中、成功和失败。
- 请求失败、扩展重启或页面切换不得静默丢弃用户输入。
- 扩展任务进度进入现有任务体验，但必须清楚标识来源扩展和结果类型，不能与正式 CAD 发布混淆。
- 长名称、长路径、缺失图标、典型数量和最大预期数量必须使用去敏虚构数据验证。

### UI-005：键盘、视口与可访问性

- 所有启停、配置、运行、取消、返回和结果操作可由键盘完成。
- 对话框、抽屉和嵌入容器必须定义 Esc、焦点圈闭、焦点归还和错误聚焦行为。
- 在项目规定的桌面基准视口、最小支持视口、浅深主题和 200% 缩放下，核心任务入口不得被遮挡或截断到不可理解。
- 文字必须在可见正文中表达关键状态；`title`、tooltip 和 `aria-label` 不能代替肉眼可见的主要信息。
- 扩展页面不得造成整页横向溢出；确需宽数据表时只允许在受控内容区滚动。

### UI-006：设计与实施门禁

- 每个扩展 UI 子项目在 G0/G1 明确用户、任务、范围、非目标和可观察成功标准。
- G2 必须覆盖正常、空、慢请求、失败、重试、依赖缺失、停用、长文本和未保存输入。
- G3/G4 必须比较实质不同的方向或说明沿用既有模式的理由，并冻结可操作 Demo、关键截图、主题和视口。
- G5 必须把每个数据和状态映射到真实 Capability、任务、Artifact 或宿主状态，不用演示值填补接口缺口。
- G6 建立“需求 → 设计证据 → 实施任务 → 自动测试 → 设计 QA → 真实验收”追踪矩阵。
- G7 按可独立演示的纵向能力分批实施；需求缺口退回 Spec，不在代码中临场决定。
- G8 使用相同数据、视口、主题和展开状态比较冻结设计与生产实现。
- G9 必须在打包后的 Windows 桌面壳验证启停、文件导出、sidecar、Explorer、下载和适用的 AutoCAD 边界。

## 12. 安全与可靠性要求

### SEC-001：正式工程写入权

- 只有宿主安全内核能够发布正式 DST/DWG。
- 任何扩展产生的候选文件在发布前均视为不可信结果，必须验证身份、范围、格式和基准。
- 扩展不得绕过永久 before 快照、文件锁、整批发布、日志或启动恢复。

### SEC-002：路径与进程

- 所有路径由宿主从工作区、用户明确选择或任务目录派生并验证；扩展输出的相对路径不得逃逸允许根目录。
- 外部进程使用结构化参数启动，禁止 `shell=True`、`cmd /c` 或字符串命令拼接。
- sidecar 和受控 CAD 作业必须有任务身份、超时、关闭和遗留进程处理规则。
- 受控 CAD 作业只能运行登记的固定 SCR 及其声明的随包 Worker/AutoLISP 依赖，并且不存在从 Artifact 返回正式工作区的写入路径。

### SEC-003：网络与凭据

- 扩展声明网络需求和目标平台；首期扩展平台不允许未声明的后台联网。
- 凭据只通过宿主代理短期提供，不写入日志、Artifact、工程目录或扩展普通设置。
- 认证失效与网络失败不得导致本地工程被部分修改。

### SEC-004：故障隔离

- 非核心扩展异常不得终止宿主、Worker、发布恢复或其他扩展。
- 同进程扩展被视为受信代码，但仍必须经过能力边界；高风险或依赖复杂的扩展使用独立进程。
- 同进程扩展的 CPU、内存与事件循环占用治理规则及宿主保护由对应 Spec 定义，纳入扩展生命周期设计。
- 扩展停止、升级或崩溃后，宿主能够识别未完成任务和待清理资源，不把未知状态报告为成功。

## 13. 推荐的能力演进顺序

以下为按产品风险控制划分的能力演进顺序，不是实施 Plan，也不绑定版本或日期。每一阶段均应有独立 Spec、设计门禁和 Plan。

1. **扩展基础与只读试点**：扩展清单、启停、状态、受限只读快照、UI 贡献点，以“导出图纸目录”验证完整链路。
2. **Artifact 与成果打包**：统一成果、任务和导出体验，验证长任务、文件范围和失败清理。
3. **受控 AutoCAD 作业**：复用现有 CAD 任务与运行时能力，引入内部作业登记、结构化参数、任务副本、固定 SCR/Worker/AutoLISP、受保护不变量校验和 Artifact-only 输出。
4. **业务平台连接器**：引入凭据、网络、同步差异、冲突和幂等语义。
5. **嵌入应用与候选 DWG**：引入 sidecar、隔离页面、候选文件和复杂发布协调。
6. **可选 TypeScript sidecar 内核**：只有在多个 TypeScript 扩展真实复用生命周期和依赖注入时，才评估在 sidecar 内使用 Cordis；不影响 Python 宿主权威。

## 14. 验收标准

本节规定可核验的验收标准，是验收的唯一权威来源；§6.2 的可观察成功结果用于产品目标表述，不构成并列的验收依据。

### AC-001：核心可用性

- 禁用全部非核心扩展后，DST Manager 能正常启动、打开工作区并执行既有核心流程。
- 任一扩展清单损坏、依赖缺失或启动失败时，其他扩展和核心宿主不受阻断。

### AC-002：启停与清理

- 启用扩展后只出现其声明的入口、设置和能力；停用后这些贡献完整移除。
- 停用期间存在活动任务时，界面明确显示等待原因，发布或恢复不被强制中断。
- 停用完成后不存在遗留路由、监听器、计时器、临时占用或 sidecar 进程；失败时有可核验诊断。

### AC-003：只读试点

- 图纸目录扩展仅使用带修订身份的只读快照即可生成目录 Artifact。
- 只读打开与导出不会创建工程管理目录、修改 DST/DWG 或改变样本原件时间戳。
- 基准变化后旧导出任务或结果能够明确标记来源修订，不冒充当前结果。

### AC-004：候选变更

- 测试扩展无法取得直接写入能力，只能提交结构化 Proposal。
- Proposal 必须经过现有预览、确认、基准、CAD、验证和发布门禁；任一步失败正式文件保持一致旧状态。

### AC-005：Artifact 与打包

- 成功成果具有来源、版本、修订、清单和哈希；失败成果不会显示为可交付完成品。
- 路径越界、缺失文件、同名冲突、磁盘不足和执行中漂移均有阻断或明确裁决。

### AC-006：受控 CAD 作业、连接器和嵌入应用

- 受控 CAD 作业只能由已登记的内部扩展发起；任意 SCR、AutoLISP、程序集、AutoCAD 命令或可执行文件输入均被拒绝。
- 作业只在任务专用副本上运行，能够超时和终止，且不存在 `Change Proposal`、正式发布或回写源工程的能力路径。
- 打印作业不会改变输入副本；普通派生 DWG 的布局与 DST 受保护不变量保持不变；归档副本解除 DST 关联后被标记为 `detached`，不能作为 DST Manager 工作区打开或回写。
- 失败、超时、验证不通过或只产生部分文件时，不登记可交付的成功 Artifact。
- 连接器认证、网络失败、冲突和部分成功具有可恢复状态，凭据不进入日志和成果。
- 嵌入应用崩溃或关闭后宿主保持可用；候选 DWG 只能由宿主安全发布。

### AC-007：前端体验

- 扩展中心和每个扩展页面完成对应 G0～G9 门禁，追踪矩阵不存在未覆盖必需项。
- 默认、加载、空、失败、依赖缺失、不兼容、停用和任务中状态均有生产可复现证据。
- 键盘、Esc、焦点归还、浅深主题、最小支持视口和 200% 缩放通过自动检查、设计 QA 和适用的真实桌面验收。
- 自动测试通过、设计一致和真实桌面可用分别记录，不以其中一种证据替代另外两种。

### AC-008：兼容与发布

- 打包产物可以列出所含扩展及版本，不兼容扩展被安全阻止。
- rc 真实业务验证覆盖扩展启停、设置、成果、失败隔离和核心回归。
- 发布记录能够从扩展版本追溯到宿主版本、commit 和对应构建产物。

### AC-009：能力最小授权（对应 EXT-003）

- 测试扩展只能取得清单声明、宿主已允许且当前可用的能力；未声明或未获允许的调用被拒绝并记录可追溯日志。
- 扩展无法取得完整应用服务、数据库会话、AcSm 可写 DOM、发布器或未受约束的正式文件路径。

### AC-010：扩展任务恢复（对应 EXT-007）

- 应用重启后，扩展任务能够区分可恢复、可重试、已中断和需人工检查，并保留来源扩展、阶段与错误信息。
- 单个扩展失败不会使其他扩展任务或 CAD 发布任务失去状态所有权。

### AC-011：运行时能力选择（对应 EXT-012）

- 任务按声明所需能力选择可用运行时；运行时缺失、不匹配或能力不足时，扩展在执行前获得明确诊断，不静默选择其他版本。

### AC-012：设置隔离与升级（对应 EXT-013）

- 扩展设置按 `extension_id` 隔离，并与应用设置、凭据分区展示；无效设置阻止对应扩展激活但不阻止宿主启动。
- 扩展升级后兼容设置被保留或显式迁移；迁移失败时保留旧数据与可恢复信息。

## 15. 后续文档拆分要求

本文接受后，后续设计不得用一份巨大 Spec 覆盖全部扩展类型。至少按以下主题分别立项：

- 扩展清单、生命周期、Capability 与 UI 贡献点；
- Artifact、扩展任务与成果打包；
- 受控 AutoCAD 作业登记、执行与 Artifact-only 边界；
- 业务平台连接器与凭据；
- sidecar 与嵌入应用协议；
- AutoCAD 运行时能力注册。

每个主题按实际影响选择 Spec、Architecture 或 ADR，并在形成明确交付阶段后再创建 Plan。本文处于 `draft` 时，不代表任何扩展功能已立项或承诺版本。
