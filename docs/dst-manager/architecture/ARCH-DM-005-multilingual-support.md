# DST Manager 多语言支持架构

> 状态：已接受（2026-09-08 按 ARCH-DM-005 架构审查闭合 P2/P3 契约问题）。
> 首期语言：简体中文（`zh-CN`）与英文（`en-US`）。
> 核心裁决：前端负责用户界面翻译，后端负责稳定的错误码、文案键和插值参数；语言选择不得改变 DST、DWG、任务或发布事务的业务语义。

## 1. 背景与目标

当前 Vue 界面、设置元数据、API 错误、诊断消息和 ShellBridge 错误中存在大量直接写入的中文文案。前端既消费业务数据，也直接展示后端返回的中文标签与消息。这种结构无法可靠切换语言，且会使语言选择渗入任务、日志和领域模型。

本设计建立一条可逐步迁移、保持现有契约兼容的多语言路径，目标如下：

- 首期完整支持 `zh-CN` 与 `en-US`，并允许后续增加语言包；
- 新安装默认跟随 Windows/WebView2 语言，用户可在设置中心显式覆盖；
- 保存语言设置后无需重启，全应用立即切换；
- 保持 API 稳定字段、错误码、任务状态、DST/DWG 内容和发布安全流程不变；
- 允许现有中文文案按功能域渐进迁移，不要求一次性重写后端内部消息。

## 2. 范围与非目标

### 2.1 首期范围

首期覆盖所有会在桌面应用中直接呈现给用户的内容：

- 应用外壳、导航、页面、对话框、表格、表单、空状态、Toast、确认提示和辅助说明；
- `aria-label`、工具提示、占位符和其他无障碍文本；
- 设置中心的分类、标签、枚举选项、校验消息与诊断横幅；
- 预览、修复、修订、任务进度及失败建议；
- ShellBridge 驱动的原生文件选择器标题、过滤器显示名和用户可见错误；
- 日期、数字、数量与复数形式的区域化显示。

### 2.2 非目标

首期不翻译以下内容：

- CLI 输出、运行日志、操作日志和开发排障详情；
- 项目文档、代码注释和发布脚本输出；
- DST/DWG 中的图纸名称、图号、布局名、自定义属性名与属性值；
- 文件路径、版本号、协议字段、API 路径、错误码、任务状态和第三方固定名称；
- AutoCAD 自身界面或第三方组件提供的文本。

语言切换不得改写既有业务数据，不得触发工作区修订，也不得创建 `.dst-manager/`。

## 3. 方案裁决

采用“前端翻译、后端提供稳定语义”的方案。

Vue 应用维护语言状态和绝大多数翻译资源。后端不维护会话语言，不接收 `Accept-Language`，也不把语言固化进草稿、任务、SSE 事件、数据库或发布日志。后端仅在接口边界为用户可见信息提供稳定的 `code`、`message_key` 和 `params`，并在兼容期保留既有中文 `message`。

不采用后端按请求语言生成文本的方案，因为 API 与 CAD Worker 是独立进程，任务又可跨请求持续执行；让后端选择语言会把会话偏好传播到任务队列、持久化与恢复流程。不采用前后端共用完整语言包的方案，因为它会让 Python 打包与 Vue 构建共享同一资源格式，而首期只有原生 Shell 边界确实需要前端之外的本地化文本。

## 4. 语言模型与解析规则

### 4.1 配置字段

在现有 Pydantic `Settings` 和设置注册表中新增：

```python
ui_locale: Literal["system", "zh-CN", "en-US"] = "system"
```

该字段作为普通应用设置写入 `%LOCALAPPDATA%\dst-manager\settings.json` 的 `values`，只保存显式覆盖值。它不进入工作区、草稿或数据库。新增带默认值的已知键保持现有 `schema_version`，无需数据库迁移。

允许通过 `DST_MANAGER_UI_LOCALE` 提供环境值，沿用设置中心既有的“默认值 < env < `settings.json` 文件覆盖”优先级：环境变量可提供安装或启动环境的默认语言，用户显式保存的文件覆盖仍具有最高优先级。API 的 `source` 继续据实返回 `default`、`env` 或 `file`。

设置中心将它显示在新的“界面”分类中，枚举项为“跟随系统”“简体中文”“English”。选择“跟随系统”时同时展示当前解析结果。

### 4.2 生效语言

前端把设置值解析为生效语言：

1. `ui_locale` 为 `zh-CN` 或 `en-US` 时直接采用；
2. `ui_locale` 为 `system` 时读取 `navigator.languages`，没有该值再读取 `navigator.language`；
3. 系统语言以 `zh` 开头时采用 `zh-CN`，其余系统语言采用 `en-US`；
4. 无法读取系统语言时采用 `zh-CN`，保证与当前产品基线兼容。

应用启动时先读取设置快照并解析语言，再挂载 Vue 根组件，避免首屏语言闪烁。设置读取失败不得阻止应用启动；此时使用系统解析结果，并保留现有设置加载错误处理。

### 4.3 保存与即时切换

语言与其他设置沿用同一个乐观并发保存流程。只有 `PUT /api/settings` 成功后才更新全局生效语言；出现 `409`、`422` 或网络错误时继续使用原语言。成功切换时同步更新 `<html lang>`，但不重新加载页面，且必须保留当前标签、焦点、选区、未保存输入、草稿与任务进度。

## 5. 前端组件

### 5.1 i18n 入口

前端引入 `vue-i18n`，由独立的 i18n 入口负责：

- 声明 `SupportedLocale = "zh-CN" | "en-US"`；
- 创建并导出唯一 i18n 实例；
- 解析系统语言和设置值；
- 切换运行时语言并更新 `<html lang>`；
- 提供日期、数字和复数格式配置。

语言资源按功能域拆分为 `common`、`shell`、`sheets`、`properties`、`revisions`、`jobs`、`settings` 和 `errors`。每个域分别提供中英文资源，构建期合并。禁止把所有文案继续堆入 `App.vue` 或单个超大词典文件。

### 5.2 翻译键与动态文本

翻译键使用稳定的语义路径，例如：

```text
sheets.toolbar.addSheet
settings.locale.system
errors.settingsConflict
jobs.status.cadRunning
```

不得使用中文原文作为键。动态内容必须使用命名参数、数量格式和复数规则，禁止在调用点拼接句子。文件路径、图号、属性值、版本号和 CAD 标识作为普通参数原样展示，不做区域化转换。

`zh-CN` 是运行时缺失键的回退语言。发行构建必须校验中英文键集合完全一致，因此回退只用于开发故障和兼容保护，不是允许混合语言的交付策略。

### 5.3 布局与无障碍

英文文案按比中文长 30% 至 60% 设计。控件优先使用弹性宽度、合理换行和可访问的溢出呈现，不通过缩小字号解决。语言切换后，按钮名称、表头、提示、`aria-label`、`title` 和占位符必须在同一个渲染周期内一致更新。

日期和数字通过 `vue-i18n`/`Intl` 格式化；业务标识、存储值和 API 负载保持原始格式。

## 6. API 与设置元数据契约

### 6.1 设置元数据

设置注册表从“保存中文显示文本”演进为“保存稳定显示键并保留兼容文本”。`SettingsItemModel` 增加：

- `label_key: str`；
- `category_key: str`；
- `file_filter_key: str | None`；
- `file_kind: Literal["exe", "dll"] | None`。

`file_filter_key` 只负责过滤器的本地化显示名，`file_kind` 负责选择固定扩展名，前端不得再通过检查中文 `file_filter` 是否包含 `exe`/`dll` 推导行为。`EnumOptionModel` 增加 `text_key: str`，其 `value` 从 `int` 扩展为 `int | str`，用于承载 `ui_locale` 的字符串枚举值。注册表中的 `_ENUM_TEXTS` 演进为“稳定选项键 + 中文兼容文本”，不能继续假设全部枚举值都是 `int`。

既有 `label`、`category`、`text` 和 `file_filter` 只保留到阶段三验收。移除前必须完成仓库内调用方、OpenAPI、TypeScript 契约与测试检查；当前同包桌面交付不存在需要跨版本兼容的旧前端。字段顺序和现有设置键保持稳定；新增 `ui_locale` 后，禁止继续用固定数量或固定索引断言注册表完整性。

### 6.2 通用错误结构

用户可见错误采用以下增量兼容结构：

```json
{
  "code": "SETTINGS_CONFLICT",
  "message_key": "errors.settingsConflict",
  "params": {},
  "message": "设置已被其他进程修改"
}
```

前端按以下顺序渲染：

1. 已知 `message_key` 与合法 `params`；
2. 前端对稳定 `code` 的过渡映射；
3. 兼容期后端原始 `message`；
4. 通用未知错误文案，同时把原始详情保留在诊断区域。

前端 `code` 映射仅用于旧错误尚未获得 `message_key` 的迁移期，必须随阶段三收敛删除，避免与后端键映射长期双份维护。已知错误的中文 `message` 同样在阶段三验收后移除；无法结构化的第三方或未知错误仍可保留原始 `message`，但只能作为诊断详情，不能充当正常界面翻译。

设置逐字段校验错误使用独立的 422 结构：

```json
{
  "code": "SETTINGS_VALIDATION_FAILED",
  "errors": {
    "cad_max_parallel": {
      "code": "SETTING_INTEGER_RANGE",
      "message_key": "settings.validation.integerRange",
      "params": {"min": 1, "max": 10},
      "message": "最大并行任务数必须介于 1 和 10 之间"
    }
  }
}
```

外层对象键 `cad_max_parallel` 是稳定设置键。前端用该键在设置快照中取得 `label_key` 并先解析字段标签，再将标签与 `min`、`max`、`allowed_values` 等结构化参数交给翻译函数。`params` 禁止携带后端已经本地化的 label、枚举文本或完整句子。阶段三验收后，逐字段对象中的中文兼容 `message` 与其他兼容字段一并移除。

字段校验错误、DST 诊断、任务失败建议和 ShellBridge 错误遵循同一稳定标识原则，但允许按功能域渐进迁移。接口层负责把已有领域错误码映射为文案键和结构化参数；领域层、基础设施层和日志记录继续使用稳定错误码及原始技术消息，不依赖 i18n。

### 6.3 SSE 与任务

SSE 继续传输 `QUEUED`、`STAGING`、`CAD_RUNNING`、`VERIFYING`、`PUBLISHING` 等稳定状态值，由前端翻译状态名称。任务记录和事件不得保存用户语言。动态失败详情只有能可靠拆分时才提供参数；无法结构化的第三方或系统错误作为原始诊断详情展示，不进行不准确翻译。

## 7. ShellBridge 边界

原生文件选择器需要本地化标题与过滤器显示名。前端在调用 ShellBridge 前生成显示文本，并调用 `select_file(file_kind, localized_description)`；桥层的 `file_kind` 支持 `dst`、`template`、`exe` 与 `dll`。Shell 根据 `file_kind` 改为映射固定扩展名白名单，只把 `localized_description` 用作对话框描述，不能接受前端提供的任意扩展名或路径规则。

这是对现有 `select_file(file_types: list[str])` 任意过滤器字符串透传行为的有意破坏性收紧，不是既有能力的延续。桌面前后端作为同一个 onedir 包发布，签名变更随同包版本一次生效，不支持“旧壳 + 新前端”的生产组合。所有 `dst`、`template`、`exe` 与 `dll` 调用点必须在同一阶段迁移。

浏览器开发态没有 ShellBridge 时沿用现有降级：设置中心“浏览”按钮禁用，工作区入口继续使用无壳路径输入流程；不得用浏览器任意文件过滤器模拟 Shell 白名单。检测到旧或部分桥而没有新签名能力时视为桥不可用，不回退到旧的任意字符串透传。

ShellBridge 错误响应增加可选的 `messageKey` 和 `params`，保留现有 `code` 与 `message`。这部分是原生 UI 边界的轻量适配，不把完整前端语言包复制到 Python。

## 8. 数据流

### 8.1 启动

1. 前端启动入口请求 `GET /api/settings`；
2. 从快照读取 `ui_locale`，缺失时视为 `system`；
3. 解析生效语言并初始化 i18n；
4. 更新 `<html lang>` 后挂载 Vue；
5. 设置请求失败时按系统语言启动，并显示既有非阻断错误。

### 8.2 设置切换

1. 用户在设置中心修改语言；
2. 前端把 `ui_locale` 与其他改动一起提交；
3. 后端按现有修订号和全量校验规则原子保存；
4. 成功响应成为新的设置快照；
5. 前端解析并切换生效语言；
6. 保存失败时不切换语言，保留表单与错误提示。

### 8.3 错误呈现

1. 领域或基础设施产生稳定错误码与原始详情；
2. 接口适配层为已知用户错误补充 `message_key` 和参数；
3. 前端按文案键本地化；
4. 未知错误使用兼容回退，同时保留原始详情供排障。

## 9. 分阶段迁移

### 9.1 阶段一：基础设施与通用界面

- 引入 `vue-i18n`、支持语言类型、语言解析器和键一致性检查；
- 新增 `ui_locale` 设置及设置元数据键；
- 改造启动顺序和设置保存后的即时切换；
- 迁移应用外壳、设置中心、通用对话框、Toast 和无障碍文本。

该阶段结束时，语言设置可工作，但尚未迁移的业务页允许暂时通过 `zh-CN` 兼容文本显示；不得宣称英文支持已完成。

### 9.2 阶段二：业务功能域

- 依次迁移图纸、属性、修订、任务、预览、修复和诊断界面；
- 把状态名称、列标题、确认文案和动态摘要改为语义键与参数；
- 调整布局以适应英文长度；
- 把依赖中文可见文本的 Playwright 选择器替换为 role、稳定属性或 `data-testid`。

### 9.3 阶段三：API 与 Shell 错误

- 为所有会进入桌面界面的 API 错误补充结构化文案字段；
- 为设置校验、DST 诊断、任务失败建议和 ShellBridge 错误建立映射；
- 迁移逐字段 422 结构、`file_filter_key`/`file_kind` 及全部 `select_file` 调用点；
- 保留日志和第三方原始详情，不在领域层引入翻译依赖；
- 重新生成 OpenAPI 与 TypeScript 契约。

阶段三验收包含兼容字段收敛：检查全部仓库内消费者后删除 `label`、`category`、`text`、`file_filter` 和已知错误的中文 `message`，同时删除前端 `code`→文案键过渡映射。未知第三方错误的原始详情不在该删除范围。

### 9.4 阶段四：完整性门禁与验收

- 启用中英文键集合一致性门禁；
- 扫描 `web/src` 的新增直接展示文本并维护允许清单；
- 完成两种语言的关键流程、视觉和无障碍验收；
- 确认不存在影响 DST、DWG、草稿和发布事务的语言分支后，才将英文支持标记为完成。

## 10. 测试策略

### 10.1 前端单元与构建检查

覆盖以下行为：

- `system` 对中文、英文、其他语言和缺失浏览器语言的解析；
- 显式 `zh-CN`/`en-US` 覆盖系统语言；
- 保存成功后即时切换，保存失败时保持原语言；
- 文案参数、数量与日期格式；
- `<html lang>` 更新；
- 中英文键集合、值类型与插值参数一致；
- 422 逐字段错误在两种语言下使用稳定设置键解析标签，参数中不存在已本地化文本；
- `file_filter_key` 在英文设置中心无中文残留，`file_kind` 不依赖显示文本推导；
- 缺失键和未知错误的回退顺序。

### 10.2 后端测试

覆盖以下行为：

- `ui_locale` 默认值、注册表元数据、字符串枚举、保存与重载；
- 非法语言值返回字段级校验错误；
- `DST_MANAGER_UI_LOCALE` 在没有文件覆盖时作为 env 来源生效，文件覆盖存在时仍由文件值优先；
- 修订冲突和 schema 阻断不改变已保存语言；
- 设置 API 的新增字段与兼容字段同时存在；
- 已纳入首期范围的错误均有稳定 `code`、`message_key` 和合法参数；
- 新增设置键不改变已有 `settings.json` 的读取兼容与原子写入保证。

### 10.3 Playwright 与视觉检查

简体中文继续运行全量 E2E。英文至少覆盖启动、打开工作区、图纸编辑、属性编辑、预览发布、设置中心、任务失败和错误提示等关键流程。两种语言均检查顶部栏、设置对话框、确认框、主表格和任务浮层的换行、截断、按钮宽度、焦点环与键盘操作。

测试不得通过硬编码中文字符串定位非文案目标。确实验证翻译结果时，测试必须显式设置语言，并断言对应语言文本。

除浏览器自动化外，必须在真实 pywebview/WebView2 桌面壳中分别验证中文与英文 Windows 显示语言，记录 `navigator.languages`、`navigator.language` 与最终解析结果；另验证 `ja-JP` 或 `de-DE` 等非中英系统语言按 §4.2 回落到 `en-US`。若 WebView2 实测不能稳定反映 Windows 显示语言，应在实施阶段回到架构审查，不得静默改用另一来源。

ShellBridge 测试必须证明 `file_kind` 只能映射登记的扩展名，前端任意字符串不能改变过滤器模式；同时验证浏览器开发态的按钮禁用和无壳路径输入行为保持不变。

## 11. 验收标准

- 新安装默认 `system`；中文 Windows/WebView2 显示简体中文，其他系统语言显示英文；
- 用户保存语言选择后无需重启即可全局切换，重新启动后保持选择；
- 两种语言的关键业务流程功能一致；
- 正常发行构建不存在缺失键或中英文混杂；
- 英文界面没有阻断操作的截断、重叠或不可访问控件；
- 所有进入桌面 UI 的首期错误均能通过稳定键本地化，未知错误仍可诊断；
- 切换语言不改变 DST、DWG、工作区修订、草稿命令、任务状态、API 稳定字段或发布结果；
- Ruff、相关 pytest、`uv lock --check`、Web 生产构建和 Playwright 关键语言矩阵通过。

## 12. 风险与约束

- 直接翻译后端自由文本会丢失动态参数或产生误译，因此只迁移有稳定错误码且能明确结构化的用户消息；
- 英文长度可能暴露既有固定宽度布局问题，布局修复必须与对应功能域迁移一起交付；
- 启动前读取设置会增加一次本地请求，失败路径必须保持非阻断；
- 兼容字段只存在于阶段一至阶段三的迁移窗口；阶段三必须以调用方检查和契约再生作为删除门禁，不能把它们遗留为无期限负债；
- 首期只定义两种语言，不引入远程语言包、在线翻译、运行时下载、翻译管理平台或用户自定义语言包。
