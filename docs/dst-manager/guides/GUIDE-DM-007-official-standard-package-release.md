# 官方图纸标准包编制、审核与随包发布指南

## 1. 适用范围

本指南面向以下人员：

- **标准编制人**：使用 DST Manager 编制候选标准、整理模板 DWG 和版本说明；
- **业务审核人**：确认属性、规则、编号、命名和图幅要求符合组织标准；
- **技术审核人**：确认标准包安全、结构合法、依赖可用，并完成 AutoCAD 验证；
- **Manager 发布维护者**：把审核通过的候选版本晋升到只读官方标准源，并随 DST Manager 绿色分发包发布。

本指南只说明**官方标准的编制、审核、晋升和分发**。普通用户在自己电脑上创建、发布和导入用户标准的操作，不等同于官方发布；从标准创建新图纸集见 PLAN-DM-036，项目合规报告见 PLAN-DM-037。

首版采用“**官方标准随 DST Manager 版本发布**”的模式，不包括：

- 在线标准商店；
- 脱离 Manager 版本的自动更新通道；
- 从网络地址自动下载标准；
- 包级数字签名和证书吊销；
- 普通用户在界面中点击“发布为官方”。

## 2. 当前实施状态

本文随 PLAN-DM-035 与 PLAN-DM-038 实施逐步落地。标准属性与 DWG 命名以 [SPEC-DM-017](../specs/SPEC-DM-017-standard-properties-and-dwg-naming.md) 为唯一权威：普通属性（文本/枚举）、派生属性（映射/组合）与全局唯一 DWG 命名模板；旧通用规则模型（`required`/`enum`/`fixed` 规则与自由目标字段）已删除。阅读时应区分“已经存在的底层契约”和“正式发布前仍需接通的发行能力”。

| 能力 | 当前权威状态 |
| --- | --- |
| 标准领域 Schema v1（普通/派生属性 + 唯一 DWG 命名模板） | 已由 PLAN-DM-038 直接替换并收口 |
| `.dststandard` 安全读取 | Task 3 正在实施；包为 ZIP，根部包含 `manifest.json` |
| 官方/用户标准库分层 | Task 3 正在实施；官方根只读，发布和导入只写用户根 |
| 标准编辑、发布检查与导出界面 | 后续任务实施 |
| 模板 DWG 实际布局检查 | Task 5 实施 |
| 官方候选版本晋升工具 | 尚未形成可供维护者调用的正式命令 |
| 官方标准随 PyInstaller 分发包打包 | 必须在首次官方发布前接入并验证 |

在“官方候选版本晋升工具”和分发包资源接线完成前，可以编制和审核候选标准，但**不得通过手工复制到程序目录的方式宣称已经完成官方发布**。

## 3. 先理解三种对象

### 3.1 用户草稿

用户草稿是可持续修改的工作对象，保存于用户标准库的草稿区域。它可以来自：

- 空白标准；
- 官方或用户已发布标准的副本；
- 现有 DST 的安全提取结果。

草稿尚未形成稳定版本，不能用于正式创建图纸集，也不能作为官方候选包提交审核。

### 3.2 已发布用户标准与候选包

草稿通过发布检查后，形成不可原地修改的用户标准版本。该版本可以导出为：

```text
<standard_id>-<version>.dststandard
```

这个文件可以作为官方审核的**候选包**，但仍不是官方标准。导出者、文件名或包内字段都不能自行赋予“官方”身份。

### 3.3 官方标准

官方标准是经过组织审核、由 Manager 发布维护者放入受信官方标准源，并随正式 Manager 分发包交付的只读版本。运行时来源由装配代码传入的 `official_root` 决定，逻辑结构为：

```text
<official_root>/
└─ <standard_id>/
   └─ <version>/
      ├─ document.json
      └─ assets/
         ├─ ...基础模板 DWG
         └─ ...布局模板 DWG
```

官方身份由**受信目录和发布通道**赋予，不读取或信任包内的 `source: official` 一类自声明字段。

## 4. 两种“发布”不要混淆

| 动作 | 执行者 | 写入位置 | 结果 |
| --- | --- | --- | --- |
| 发布用户标准 | 普通用户或标准编制人 | `%LOCALAPPDATA%\dst-manager\standards\published\...` | 本机用户标准版本 |
| 导出标准包 | 普通用户或标准编制人 | 用户选择的导出目录 | `.dststandard` 候选包 |
| 晋升官方标准 | Manager 发布维护者 | 受版本控制的官方标准源 | 待随软件分发的官方版本 |
| 发布 Manager | Manager 发布维护者 | `dist/releases/` | 包含官方标准的绿色分发 ZIP |

`StandardStore.import_package()` 的用途是把包导入**用户标准库**。它不会也不应该把标准写入官方根。不得采用“先导入用户库，再手工把目录复制到官方根”作为正式晋升流程。

## 5. 角色与职责

同一个人可以承担多个角色，但检查结果必须明确记录由谁确认。

| 角色 | 必须完成 | 不应执行 |
| --- | --- | --- |
| 标准编制人 | 准备内容、模板和示例，修复检查错误，说明变更 | 自行宣称候选包为官方版本 |
| 业务审核人 | 审核属性语义、枚举值、映射目标、编号和 DWG 命名模板 | 用技术测试代替业务裁决 |
| 技术审核人 | 审核包安全、依赖、模板、双版本 CAD 与创建冒烟 | 静默修改审核通过的内容 |
| 发布维护者 | 核对证据、执行晋升和 Manager release、保留产物 | 绕过失败门禁或覆盖既有版本 |

建议至少由两个人完成最终确认：标准编制人与业务审核人不能只留下同一人的单一结论；小团队暂时无法分离角色时，也应分两个时间点执行并保留两份检查记录。

## 6. 标准身份与版本规则

### 6.1 标准身份

官方版本由以下二元组唯一标识：

```text
standard_id + version
```

例如：

```text
szmedi.gas@2.1.0
```

本产品不使用内容摘要作为标准身份。摘要可以用于传输核对或发布证据，但不能替代 `standard_id + version`，也不能因为摘要相同就复用另一个身份。

### 6.2 `standard_id`

- 一经对外发布，不因标准名称、部门名称或中文显示名变化而改变；
- 使用稳定、可读、不会与其他组织冲突的命名空间；
- 大小写差异不得产生两个标准；
- 不把年份、Manager 版本或 AutoCAD 版本塞入 ID；这些信息属于标准版本或兼容声明。

### 6.3 版本号

建议采用三段式版本：

```text
主版本.次版本.修订版本
```

- **主版本**：删改已有属性语义、派生关系、编号或资产选择，可能影响现有项目；
- **次版本**：增加字段、专业映射、模板或兼容能力；
- **修订版本**：修正文案、漏项或不改变既有语义的小错误。

已经进入官方源的 `<standard_id>@<version>` 永远不可覆盖。即使只是修正一个 DWG，也必须发布新版本。

### 6.4 旧版本保留

旧版本不能因新版本发布而删除。项目可能仍通过 `DSTManager.Standard` 绑定旧版本，项目快照丢失时需要从官方库恢复完全相同的 ID 与版本。

## 7. 发布前置条件

开始编制官方候选版本前，确认：

- 已确定标准负责人和业务审核人；
- 已分配稳定的 `standard_id`；
- 已决定本次目标版本号；
- 已整理图纸集属性和图纸属性定义；
- 已整理普通属性（文本/枚举）、派生属性（映射/组合）、全局 DWG 命名模板和编号策略；
- 已准备基础模板 DWG 与布局模板 DWG；
- 布局模板中的来源布局严格以允许图幅命名；
- 已明确支持的 AutoCAD 兼容组；
- 所需受信扩展及最低版本已经登记；
- 已准备至少一个可以人工核对的示例项目输入。

缺少任一关键业务材料时，应停留在草稿阶段，不要用空值或虚构模板“先发布再补”。

## 8. 编制候选标准

### 8.1 选择起点

在 DST Manager 标准管理界面中选择最合适的起点：

1. **空白标准**：全新的标准体系；
2. **复制已发布版本**：已有官方或用户标准的小步演进；
3. **从现有 DST 提取**：已有成熟项目，但尚未形成结构化标准。

从 DST 提取时，只把属性定义和必要安全结构带入草稿。项目子集、图纸、绝对路径、客户名称、工程编号和项目专用引用不得进入标准。

### 8.2 填写基本信息

至少核对：

- 标准 ID、版本、中文名称和说明；
- 支持的 AutoCAD 版本；
- 适用专业、设计阶段和使用限制；
- 版本变化说明；
- 扩展依赖及最低兼容版本。

### 8.3 配置普通属性与派生属性

- 属性定义 CSV 只用于批量合并**普通属性**（文本/枚举），不产生任何派生关系；
- 属性名在全部作用域与类型中全局唯一，改名保留历史名称，删除被引用属性必须阻断；
- 枚举值受控且非空，枚举属性的非空默认值必须属于枚举列表；
- “专业名称 → 专业代码”等一一对应关系使用**一条映射属性**，映射行由源枚举项固定生成；
- DWG 名称等组合值使用**组合属性**的字段令牌与固定文本；DWG 文件名使用标准级唯一模板；
- 派生属性（映射/组合）在创建表单中只读；
- 首版不使用日期格式化、通用公式、脚本或自由 JSON。

### 8.4 配置模板资产

每个资产必须有稳定 `asset_id`、明确种类和包内相对路径。模板文件一律经标准编辑器的
「选择本机模板」受控复制进草稿受控资产目录，**不能**引用编制人电脑上的外部绝对路径：

- 桌面壳下用固定 `template` 文件种类（`*.dwg;*.dwt`）选择本机文件；无桌面壳的本地开发态
  用单独标明的「来源绝对路径」输入，调用同一个端点；
- 后端把文件复制为 `assets/managed-<uuid4hex>.dwg|.dwt` 并只把受控副本名写回草稿；
  本机绝对路径不入 `document.json`、不入发布目录、不入包内 `manifest.json`；
- 单文件不得超过 64 MiB，扩展名只允许 `.dwg`/`.dwt`；来源不存在、扩展名不符、超限或复制中断
  一律拒绝并保留原声明（错误码 `STANDARD_ASSET_SOURCE_NOT_FOUND`/`STANDARD_ASSET_SOURCE_INVALID`/
  `STANDARD_ASSET_COPY_FAILED`）；
- 保存与发布成功后只清理草稿 `assets/` 下**未被当前文档引用且带 `managed-` 前缀**的副本，
  手工放置的既有资产不动；
- 「受控路径」列只显示包内相对路径；已声明但文件不在草稿受控目录内、或声明的文件指向受控目录
  之外（含符号链接）时，发布与导出被阻断。

基础模板与布局模板分开登记：

- 基础模板用于生成子集主 DWG；
- 布局模板提供需要导入的布局内容；
- `Model` 不参与图幅匹配；
- `A3` 与 `A3 `、`a3` 均不视为相同布局；
- 同一布局模板不得出现重复或含义不明的图幅布局。

## 9. 候选版本发布与导出

### 9.1 运行标准发布检查

在标准编辑器中进入“发布检查”。检查至少覆盖：

- 基本信息与标准身份；
- 普通属性（名称全局唯一、保留名称、枚举项与默认值）；
- 派生属性（映射源类型/作用域与唯一占用、目标非空、组合字段越权）；
- 映射待确认 warning 与枚举变化后的快照差异；
- 全局 DWG 命名模板（字段范围、非法文件名、缺少唯一性字段的 warning）；
- 编号、后缀、图号、标题和 DWG 命名；
- 模板文件存在性、受控路径和布局名称；
- 标准包结构和扩展依赖。

错误必须修复后才能发布。警告可以继续，但编制人必须逐条写明接受理由，不能只记录“已知警告”。

### 9.2 发布用户版本

检查通过后，先发布为不可变的用户标准版本。发布成功后确认界面已经进入只读版本详情，而不是继续显示可编辑草稿。

### 9.3 导出候选包

从已发布版本导出 `.dststandard`。候选包逻辑结构为：

```text
<standard_id>-<version>.dststandard
├─ manifest.json
└─ assets/
   ├─ ...基础模板 DWG
   └─ ...布局模板 DWG
```

`manifest.json` 使用 UTF-8。包内路径一律使用相对 POSIX 路径；不得包含盘符、绝对路径、`..` 或两个规范化后相同的路径。

导出只写入**文档声明且已通过存在性校验**的资产：草稿或发布目录里的其它文件（例如未引用的
`assets/managed-*` 孤儿副本、临时文件）不会进入候选包；声明文件缺失时导出以
`STANDARD_ASSET_FILE_MISSING` 拒绝并终止。

导出后不要再用压缩软件手工替换包内文件。任何内容变化都应回到草稿、发布新版本并重新导出。

## 10. 候选包安全检查

### 10.1 包级硬限制

当前安全读取契约包括：

- 单个条目不超过 64 MiB；
- 整包解压后总大小不超过 256 MiB；
- 必须且只能使用根部 `manifest.json` 作为标准文档入口；
- 拒绝绝对路径、盘符路径、路径逃逸和重复规范化路径；`assets/../A2.dwg` 这类含 `..` 的条目在**归一化前**即拒绝；
- 清单与包内条目必须**双向一致**：清单声明的每个文件必须存在于包内（`STANDARD_ASSET_FILE_MISSING`），
  包内不得夹带未在清单中声明的条目（`STANDARD_PACKAGE_INVALID`）；导入在建任何目录之前完成校验；
- 拒绝 Python、DLL、EXE、SCR、Shell、AutoLISP 和其他可执行内容；
- Schema 版本、标准 ID、版本、属性、DWG 命名模板、资产和依赖必须能够被严格解析。

禁止扩展名至少包括：

```text
.py .pyc .pyo .pyd .dll .exe .scr .lsp .fas .vlx
.bat .cmd .ps1 .com .sh .vbs .js .msi
```

扩展名检查不是唯一安全依据。审核人仍需确认文件实际用途，不得把可执行内容改名为 `.dwg` 或其他允许扩展名混入包内。

### 10.2 开发仓库中的基础验证

Task 3 合并后，至少运行：

```powershell
$env:UV_LINK_MODE = "copy"
uv run pytest tests/unit/test_standard_package.py tests/unit/test_standard_store.py tests/unit/test_standard_assets.py -q
uv run ruff check src/dst_manager/domain/standards.py src/dst_manager/infrastructure/standards src/dst_manager/application/standard_assets.py tests/unit/test_standard_package.py tests/unit/test_standard_store.py tests/unit/test_standard_assets.py
```

这些测试证明读取器和标准库契约没有回归，但**不能证明某个具体候选包业务正确**。正式候选包必须再经过内容、DWG 和创建流程检查。

### 10.3 不允许的替代做法

- 不能因为 ZIP 能正常解压就认为标准包有效；
- 不能只打开 `manifest.json` 看起来“像 JSON”就跳过 Schema 校验；
- 不能只核对文件名，不读取布局模板的实际布局集合；
- 不能使用用户导入成功代替官方晋升审核；
- 不能把杀毒软件未报警当成包安全结论。

## 11. 业务审核

业务审核人应在不知道实现细节的情况下，能够从标准内容和示例预览回答以下问题：

### 11.1 属性与允许值

- 图纸集属性和图纸属性是否完整；
- 必填字段是否确实在所有适用项目中必填；
- 图幅、专业、阶段等枚举是否遗漏或多放值；
- 默认值和固定值是否会把项目特有内容写进所有项目；
- 子集属性是否误当成首版强制能力。

### 11.2 映射与派生

- 每个专业名称是否都有唯一、正确的专业代码；
- 映射源是否只被一个映射属性占用，且每个源枚举项都有非空目标；
- 派生属性是否确实不允许人工覆盖；
- DWG 命名模板样例是否符合真实文件名与图号习惯；
- 流水号位数、序号后缀和不编号关键字是否与 Manager 现行策略一致。

### 11.3 模板与图幅

- 每个适用场景是否至少有一个基础模板和布局模板；
- 标准允许图幅与布局模板的实际布局是否一致；
- 模板中是否残留客户、项目、用户名、网络路径或不应分发的图块/外部引用；
- 同一子集统一图幅只作为创建流程简化，不被误写成归档验收规则。

业务审核结论必须为“通过”“退回修改”之一；有警告时逐条写明接受理由。

## 12. 技术审核

### 12.1 Schema 与属性模型

- `standard_id + version` 在官方标准源中不存在；
- 同一身份与用户库碰撞不会被错误覆盖；
- 属性引用与令牌引用的对象都存在；
- 映射源唯一占用，所需枚举全部覆盖；
- 组合与 DWG 命名不存在字段越权（组合不能引用组合，命名只用 subset 系统字段与 sheetset 属性）；
- 补零格式码只出现在 `subset.sequence` 上，宽度 1–12；
- 扩展依赖命中固定白名单，并满足最低版本。

### 12.2 资产与 CAD

- 包内每个已声明资产都存在，未声明文件有明确用途；
- 文件路径均在 `assets/` 受控范围；
- 基础模板和布局模板可由目标 AutoCAD 兼容组读取；
- AutoCAD 2016/2020 均只读枚举布局，不触发 QSAVE；
- 布局名称与图幅严格匹配；
- 资产读取失败不会留下半成品草稿或修改原 DWG。

具备本机环境时运行：

```powershell
$env:DST_MANAGER_RUN_AUTOCAD = "1"
uv run pytest tests/system_autocad -q
```

如果缺少某个 AutoCAD 版本，结论必须记录为“未验证”，不能写成“通过”。只声明支持 2020 兼容组的标准不要求伪造 2016 通过记录。

### 12.3 创建冒烟

PLAN-DM-036 可用后，对每个官方候选版本至少创建一次最小测试项目：

1. 选择候选标准版本；
2. 选择一个映射字段值并核对派生代码；
3. 建立至少一个子集和两张图纸；
4. 选择基础模板、布局模板和图幅；
5. 核对最终图号、标题、DWG 文件名、布局名和 DST 引用；
6. 执行暂存、CAD 验证和原子发布；
7. 重新打开成果并确认 `DSTManager.Standard` 等于候选身份；
8. 删除项目标准快照的临时副本，确认可以按 ID 与版本从官方库恢复。

测试只能在临时目录或专用样本副本中进行，禁止修改 `sample/` 原件。

## 13. 审核证据包

每个官方候选版本应保留一份审核记录，至少包含：

| 类别 | 必需内容 |
| --- | --- |
| 身份 | 标准 ID、版本、名称、候选包文件名 |
| 变更 | 相比上一版本的新增、修改、删除和兼容性影响 |
| 业务审核 | 审核人、日期、结论、警告接受理由 |
| 技术审核 | 审核人、日期、自动测试结果、未执行项 |
| CAD 证据 | 实际检查的 AutoCAD 兼容组和布局摘要 |
| 创建证据 | 冒烟项目输入摘要与关键派生结果 |
| 发行关联 | 包含该标准的 Manager 版本与 release 产物名 |

审核记录不得包含真实客户路径、敏感项目名称、许可证信息或私有工程文件。DWG 样本如不能公开提交，只记录受控证据位置和脱敏摘要。

## 14. 官方晋升

### 14.1 晋升前停止条件

出现以下任一情况立即停止：

- 存在未修复错误；
- 业务审核未通过；
- 候选包身份与官方源碰撞；
- 需要的受信扩展未随目标 Manager 版本提供；
- 声明支持的 CAD 兼容组没有完成所需检查；
- 候选包在审核后又被修改；
- 官方晋升工具或随包资源接线尚未完成。

### 14.2 从包形态转换为官方目录形态

候选包使用 `manifest.json`；运行时官方目录使用 `document.json`。正式晋升工具应当：

1. 使用同一个 `StandardPackageReader` 完成安全读取；
2. 解压到同盘临时目录；
3. 把已验证的 `manifest.json` 写为 `document.json`；
4. 只复制已经过路径和大小校验的资产；
5. 再次解析 `document.json`；
6. 确认目标 `<standard_id>/<version>` 不存在；
7. 使用原子 rename 提交到受版本控制的官方标准源；
8. 失败时删除临时目录，不留下半个官方版本。

在正式晋升工具提供前，不应以 PowerShell `Expand-Archive`、资源管理器复制或手工改名代替上述流程。

### 14.3 官方源的版本控制

- 每个版本独立目录，目录名必须与文档身份一致；
- 资产必须随该版本保存，不能引用另一个版本目录；
- 新版本以新增目录提交，不修改旧目录；
- 代码评审必须同时查看标准文档差异、资产清单变化和审核记录；
- 二进制 DWG 无法文本审查时，以资产检查结果和人工打开记录补足。

## 15. 随 Manager 发布

### 15.1 打包接线

官方标准源必须作为 PyInstaller `datas` 进入运行时资源目录，并由应用装配为 `StandardStore(official_root=...)`。首版 `StandardStore` 直接扫描目录，不依赖一个可被手工伪造为信任来源的包内 `source` 字段。

首次接入时必须增加打包守护测试，至少证明：

- 开发态与 frozen 态解析到正确官方根；
- `packaging/dst-manager.spec` 覆盖全部官方标准文件；
- 分发 ZIP 中不存在草稿目录和用户标准；
- 解压后的官方目录不可通过标准管理 API 写入；
- 相同 ID 与版本的用户发布或导入被稳定拒绝。

### 15.2 执行 release

确认版本号、changelog、官方标准提交和审核证据均已进入待发布提交后，使用既有 Manager release 流程：

```powershell
.\scripts\release.ps1 -Version <Manager版本>
```

该脚本要求工作区干净、位于 `main`、版本号匹配、changelog 已更新并且 tag 不存在；随后运行 Ruff、pytest、构建绿色分发包，最后创建本地 annotated tag。脚本不自动 push 或上传远程 Release。

官方标准发布不得绕过 release 门禁单独修改已生成的 ZIP。任何对 ZIP 的后处理都会使测试过的输入与实际分发内容不一致。

### 15.3 分发产物

目标产物为：

```text
dist/releases/dst-manager-v<Manager版本>-win64.zip
```

记录“标准身份 → Manager 发行版本”的对应关系，例如：

```text
szmedi.gas@2.1.0 首次随 dst-manager-v0.4.0-win64.zip 分发
```

## 16. 分发包验收

不要只验证源码运行。必须解压最终 ZIP，在真实 frozen 环境完成：

1. 启动 `dst-manager.exe`；
2. 打开标准管理页；
3. 确认官方版本可见且来源显示“官方”；
4. 确认编辑、删除和覆盖发布不可用，并显示只读原因；
5. 导出官方版本并重新用安全读取器验证；
6. 复制为用户标准，确认只能编辑新草稿；
7. 尝试导入同一身份，确认返回 `STANDARD_VERSION_EXISTS`；
8. 在具备条件时从官方标准创建测试图纸集；
9. 重启程序，确认官方版本仍存在，用户标准与官方标准分区不混淆；
10. 检查日志中没有资源路径、Schema 或依赖加载错误。

验收失败时不要分发 ZIP，也不要创建或推送正式 tag；保留现场并回到候选标准或打包接线修复。

## 17. 更新、纠错与撤回

### 17.1 发现内容错误

1. 保留已经发布的错误版本，不修改其目录；
2. 从该版本复制新草稿；
3. 修复内容并提高版本号；
4. 重新执行全部适用审核；
5. 随新的 Manager 版本发布；
6. 在版本说明中明确受影响版本和升级建议。

### 17.2 严重安全问题

如果旧包含有敏感信息或安全风险，停止继续分发受影响的 Manager ZIP，并发布修复版。是否从后续安装包移除有风险的旧版本需要单独安全裁决；即使移除，也不能把新内容伪装成原来的 ID 与版本。

已绑定旧版本的项目仍可能保存项目快照。程序不得在未获用户确认时自动改绑新版本。

### 17.3 业务规则已过时

发布新版本并把旧版本标记为不推荐使用。首版如果尚无“弃用”元数据，就在版本说明和发行说明中明确，不通过删除目录模拟弃用。

## 18. 常见问题与处理

| 现象 | 原因与处理 |
| --- | --- |
| 包能解压但 Manager 拒绝 | 查看稳定错误码；常见原因是路径逃逸、禁止扩展、缺失 manifest 或 Schema 不合法 |
| 导入候选包后显示“用户” | 正常；普通导入只进入用户库，不能产生官方身份 |
| 想修正已发布版本里的一个 DWG | 新建草稿并提高版本号，不能替换旧目录中的文件 |
| `A3` 布局检查失败但肉眼看着相同 | 检查尾随空格、大小写、全角字符和重复布局；规则采用严格匹配 |
| 只有 AutoCAD 2020 环境 | 对声明支持 2016 的标准不能给出完整通过结论；补齐环境或缩小支持声明 |
| 包依赖的扩展不存在 | 标准可以查看和导出，但不能用于创建或宣称完整验证通过；发布前补齐受信扩展 |
| 官方源已有相同 ID 与版本 | 停止晋升并提高版本号；不得覆盖或改目录大小写规避碰撞 |
| 最终 ZIP 中找不到官方标准 | 检查 PyInstaller `datas`、运行时 `official_root` 装配和打包守护测试 |
| 用户删除项目标准快照 | Manager 按 ID 与版本从官方库恢复；恢复不到时项目仍可打开，但标准校验不可用 |

## 19. 官方发布检查表

### 19.1 编制

- [ ] 标准 ID 稳定且命名空间明确。

- [ ] 扩展依赖和最低版本已声明。

### 19.2 审核
