# 前端功能设计与实施门禁通俗说明

## 1. 这份说明是给谁看的

这份说明面向不熟悉前端开发、但需要描述需求、选择界面并验收结果的人。你不需要会 Vue、TypeScript、CSS，也不需要知道组件怎样编写；你只需要在合适的时间作出业务和使用体验方面的决定。

具体检查规则以 [GUIDE-DM-001：前端功能设计与实施门禁清单](GUIDE-DM-001-frontend-design-implementation-gates.md) 为准。本文只解释为什么要设置这些门、每一阶段你应当看什么，以及哪些事情不能只交给 Agent 自行判断。

## 2. 什么叫“门禁”

门禁不是增加审批，也不是要求每一步都开会。它表示：在进入下一阶段以前，有几件关键事情必须说清楚，并留下能够复查的证据。

可以把开发界面想成装修一套办公空间：

- 需求是“哪些人要在这里完成什么工作”；
- 视觉稿是“装修效果图”；
- 交互 Demo 是“可以走进去体验的样板间”；
- Spec 是“双方确认的功能与使用规则”；
- 技术映射是“检查水电、承重墙和现有管线”；
- Plan 是“施工顺序和每一步的验收办法”；
- 设计 QA 是“拿着效果图逐项检查完工现场”；
- 真实环境验收是“真的搬进去工作一次”。

只有效果图就施工，往往会在现场发现门打不开、插座不够或者桌子放不下。前端返工的原因非常相似。

## 3. 为什么以前“已经有 Spec 和 Demo”仍然返工

Spec、Demo 和 Plan 各自只能解决一部分问题：

- Demo 很容易展示正常状态，却遗漏加载失败、没有数据、输入未保存、名称很长等情况。
- Spec 可能写了“提供打开文件夹按钮”，但没有固定按钮的可见尺寸和位置。
- Plan 可能安排了“实现按钮”，却没有安排检查按钮在真实桌面里是否看得见。
- 自动测试可能通过，因为程序能找到并点击这个按钮；但用户看到的按钮可能只剩一个小点。
- 浏览器里下载正常，不代表打包后的 Windows 桌面壳也允许下载。

因此，问题通常不是 Agent 不会写代码，而是从“你确认的设计”到“生产代码应该怎样实现和验收”之间丢失了信息。

## 4. 十道门分别在防什么

### G0：先圈定这次要做什么

这一门防止开发过程中不断扩张范围。

你需要确认：这次解决哪个问题、涉及哪些页面、明确不做什么。比如“改善图纸页浏览”不能在实施中悄悄变成“顺便重做属性页和后端数据结构”。

你应当看到：一段简短的范围、非目标和变更等级说明。

危险信号：同一句需求，不同人理解成不同页面或不同工作流程。

### G1：确认解决的是真实业务问题

这一门防止用“更漂亮”“更现代”代替目标。

你需要说明：谁在什么情况下使用、当前哪里费劲、改善后怎样判断更好。例如“长子集名称无需反复悬停即可识别”就比“树形导航更好看”更容易设计和验收。

你应当看到：核心用户任务、业务限制和可观察的成功标准。

危险信号：只有页面名称和功能列表，没有人能完整讲出一次实际操作。

### G2：把顺利和不顺利的情况都列出来

这一门防止只设计一张漂亮的默认页面。

你不需要设计技术状态，但需要回答日常问题：没有数据时看到什么？输入一半切换标签怎么办？保存失败会不会丢输入？名称特别长怎样读？任务执行很久时用户在哪里看进度？

你应当看到：一条完整操作路径和一张状态清单，包括加载、空数据、失败、编辑中、危险操作、窄屏和大数据量。

危险信号：只有“正常打开页面”的截图；一问失败或取消会怎样，答案是“开发时再决定”。

### G3：选择真正不同的视觉方向

这一门防止过早在一个粗糙模板上修修补补。

你主要判断：信息顺序是否符合工作习惯，最常用的操作是否醒目，危险操作是否容易误点，数据很多时是否还能读。不要只凭颜色、阴影或者第一眼的“高级感”选择。

你应当看到：使用相同数据和相同业务目标的不同方案，以及推荐理由。

危险信号：三个方案只有颜色不同；为了画面清爽而删除真实业务中必须出现的信息。

### G4：把选中的设计冻结下来

这一门防止你确认的是 A，开发过程中却逐渐变成 B。

“冻结”不表示以后不能改，而是任何改变都要被看见和确认。应固定关键状态的 Demo 或图片、视口大小、浅深主题、主要尺寸、滚动方式，以及 Demo 中哪些只是模拟。

你需要亲自操作核心流程，特别留意：能否找到入口、是否看得懂当前状态、误操作能否返回、失败后输入是否还在。

危险信号：Demo 永远使用“最新版”但没有固定截图；Demo 中的按钮和字段在 Spec 里找不到依据。

### G5：让技术人员检查“样板间能否盖成真楼”

这一门是以前最容易缺失的环节。

Agent 或技术负责人需要阅读现有代码，把 Demo 中的每个数据、按钮和状态映射到真实 API、组件和桌面能力，同时寻找全局样式冲突、性能风险和现有结构限制。

你不需要判断修改哪个文件，但应该听懂这些结论：哪些可以直接实现，哪些需要后端配合，哪些只能模拟，哪些设计需要作取舍。

危险信号：还没有看现有代码就开始写 Plan；关键数据来源被回答为“先写界面，以后再接”。

### G6：证明计划没有漏项

这一门防止把一份很长的 Plan 误认为一份完整的 Plan。

最重要的不是计划有多少页，而是每条要求能否沿着一条线找到：在哪个 Demo 状态看过、由哪个任务实现、由哪个测试检查、最终由谁验收。这叫追踪矩阵。

你主要检查：自己的每个重要要求是否都在表里，最终哪些地方需要你亲自确认。

危险信号：任务写“完善页面样式”“处理异常”“增加相关测试”，却没有具体对象、结果和验收方法。

### G7：分小批施工，每批都能检查

这一门防止几天或几周后一次性看到完整结果，发现方向早已偏离。

比较稳妥的批次不是“先写所有 HTML，再写所有 CSS，最后接 API”，而是每批完成一小段真实任务。例如先完成“打开工作区并正确显示身份”，确认后再做“浏览和筛选图纸”。

你不需要检查每次代码提交；但涉及核心操作或视觉方向的批次，应尽早看一次生产预览。

危险信号：整个计划实施完之前没有任何可操作的生产页面；发现需求不清时，实施者直接选择一种行为继续写。

### G8：拿确认过的设计和生产实现逐项对照

这一门不是问“整体看起来还可以吗”，而是让比较条件保持一致。

Demo 和生产截图必须使用相同数据、窗口大小、主题和展开状态。否则两张图即使放在一起，也很难判断差异来自实现还是状态不同。

你主要判断：信息层级、入口是否明显、文字是否读得全、操作反馈是否符合预期。Agent 负责检查尺寸、焦点、键盘、溢出和自动测试。

危险信号：只说测试全部通过；拿 Demo 默认态与生产编辑态比较；差异被口头称为“小问题”但没有记录是否接受。

### G9：在真实工作环境中走一遍

这一门防止“浏览器里能用，交付程序里不能用”。

DST Manager 还涉及 Windows 桌面壳、文件系统、Explorer、下载和 AutoCAD。它们中的一部分不能只靠浏览器模拟证明正确。

你需要在实际交付入口完成一次核心任务。涉及真实工程时使用副本，并遵守项目的授权和安全要求。

危险信号：只在开发服务器演示；真实环境没有执行却写成“验收通过”；“功能已经实现”被当作“用户已经验收”。

## 5. Figma 到底要不要用

Figma 不是必需步骤，也不能自动减少返工。它擅长的是：

- 固定画面尺寸、间距和组件样式；
- 管理按钮、输入框、表格等组件的不同视觉状态；
- 让你直接在画面上评论；
- 保存清晰的视觉基准。

Figma 不擅长证明：

- 复杂编辑流程是否真的顺手；
- 数据刷新、保存失败和草稿状态怎样变化；
- API 是否提供所需数据；
- Windows 桌面壳、下载和 AutoCAD 是否可用；
- 生产代码有没有受到全局 CSS 影响。

对 DST Manager 这种数据和状态较多的桌面 Web 界面，可操作 HTML Demo 往往比纯 Figma 更适合确认交互。如果已有版本化 Demo、固定截图、设计令牌和状态矩阵，可以不使用 Figma。如果使用 Figma，应明确它是视觉基准，并固定具体 frame/version；不要让 Figma 和 Demo 各自保留一套不同答案。

## 6. 哪些事情必须由你确认

你最适合确认：

- 实际业务目标有没有被理解正确；
- 信息顺序和常用操作是否符合你的工作习惯；
- 文案和状态提示是否容易理解；
- 哪个视觉方向更适合长期使用；
- 某个与 Demo 不同的生产效果是否可以接受；
- 在真实桌面程序中是否完成了工作任务；
- 哪些非关键问题可以留到后续。

这些决定不能只交给 Agent，因为它们没有唯一的技术正确答案。

## 7. 哪些事情应由 Agent 或技术负责人负责

你通常不需要判断：

- 应该拆成多少 Vue 组件；
- 状态保存在 composable、组件还是服务端；
- CSS 应怎样隔离；
- API 字段、类型和错误码如何映射；
- 应写哪些单元测试或 Playwright 测试；
- 性能、安全、并发和发布事务怎样保证；
- 哪些文件需要修改以及实施顺序。

但是，技术负责人必须把会影响你选择的结果翻译成通俗语言。例如：“如果保留这个操作方式，需要新增后端接口，会多一个实施阶段”，而不能只给出技术术语。

## 8. 你每次只需要问的八个问题

如果不想逐条阅读完整清单，可以在评审时反复问下面八个问题：

1. 这次明确解决哪个用户问题，明确不做什么？
2. 除了正常状态，失败、空数据、编辑一半和极端数据是什么样？
3. 我现在确认的版本是否已经固定，之后的差异怎样记录？
4. Demo 中每个数据和操作在真实系统里从哪里来？
5. Spec 的每条重要要求在 Plan 的哪个任务里？
6. 每条要求最后用什么证据证明，而不只是证明代码存在？
7. Demo 和生产实现是否在完全相同的状态下比较过？
8. 是否在真正交付的 Windows 桌面程序里走完了核心任务？

如果其中任何一个问题没有明确答案，就不应急着进入下一阶段。

## 9. 三种常见误区

### “Agent 已经理解了，不需要写那么细”

对话中的理解不会自动进入下一次实施上下文。重要决定必须进入权威 Spec、冻结设计或追踪矩阵，否则换一个 Agent 或隔几天继续时很容易丢失。

### “测试全通过，所以页面应该没问题”

测试可能只检查按钮存在、可以聚焦和事件被触发。它不一定检查按钮是否只有几像素、文字是否被截断、完整路径是否挤坏表格。自动测试必须与截图检查和真实使用配合。

### “先实现出来，我最后统一提意见”

最后统一检查会让早期结构错误扩散到组件、样式、测试和文档。分批预览不是让你反复参与技术细节，而是在返工仍便宜时确认方向。

## 10. 一个简化例子

假设需求是“在顶栏增加打开图纸集所在文件夹的入口”。

只写 Plan 时，可能得到：增加一个按钮、调用桌面壳、补点击测试。按钮即使被 CSS 压成小点，测试仍可能通过。

通过门禁后，过程会多出几个关键答案：

- 业务目标：用户能从当前图纸集身份旁明显找到入口；
- 设计冻结：桌面宽屏使用可读文字或明确图标，点击区域有固定下限；
- 技术映射：现有全局按钮 padding 会覆盖图标按钮，必须收敛样式；
- 追踪矩阵：行为测试检查调用目标，可见结果测试检查按钮文字和尺寸；
- 真实验收：在打包桌面程序中点击，Explorer 打开正确目录并尽可能选中 DST。

这不是为了把一个按钮复杂化，而是为了让“代码里有按钮”真正等于“用户能用这个按钮完成任务”。

## 11. 发现问题时该退回哪里

- 发现业务目标理解错了：退回 G0/G1。
- 发现漏了失败、取消或未保存状态：退回 G2。
- 选中的布局不适合真实数据：退回 G3/G4。
- Demo 依赖生产系统没有的数据或能力：停在 G5，先作技术裁决。
- Plan 没有覆盖 Spec：停在 G6，补任务和验证。
- 实施结果偏离确认设计：停在 G7/G8，修复或请你接受差异。
- 浏览器能用但桌面程序不能用：停在 G9，不能宣布完成。

退回不是失败，而是在问题尚未扩大时修正。真正昂贵的是发现问题后仍继续实施。

## 12. 怎样理解“完成”

以下三句话含义不同：

- **已实现**：代码已经写入。
- **已验证**：规定的自动检查和设计 QA 已取得证据。
- **已验收**：你在真实使用方式下确认核心任务可完成，并接受剩余差异。

以后看到计划状态时，应确认它说的是哪一种。只有必需门禁全部通过，才能把前端功能称为“完成”。
