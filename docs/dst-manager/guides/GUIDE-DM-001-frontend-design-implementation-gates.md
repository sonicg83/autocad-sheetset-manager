# DST Manager 前端功能设计与实施门禁清单

## 1. 目的与适用范围

本清单用于把一个前端想法安全地推进为可验收的生产功能，重点防止以下返工来源：

- 只确认默认画面，没有确认加载、空数据、错误、编辑中和窄屏等状态；
- Demo、Spec、实施计划和生产代码分别作出不同假设；
- 计划只写“实现页面”，没有逐条覆盖业务规则和异常路径；
- 自动测试只证明元素存在，没有证明用户看得见、读得懂、能完成任务；
- 浏览器 Demo 可用，但桌面壳、真实数据或 Windows 原生能力不可用；
- 视觉验收留到开发结束才进行，偏差累积后集中返工。

本清单适用于 DST Manager 的新页面、新用户流程、现有页面重构和影响交互行为的改动。纯后端、纯文档和不改变用户可见结果的内部重构不适用。

本文是门禁规则的唯一权威来源。面向非前端专业人员的解释见 [GUIDE-DM-002](GUIDE-DM-002-frontend-gates-plain-language.md)。

## 2. 基本原则

1. **没有证据，不算通过。** “已经考虑”“应该没问题”不能作为门禁结论。
2. **上一门未通过，不进入下一阶段。** 可以开展不依赖该结论的只读调研，但不得据此冻结设计或开始生产实施。
3. **一条要求只有一个权威来源。** Spec 约束行为，选定 Demo 或 Figma 约束视觉，Plan 约束实施顺序；其他文档只能引用，不复制出另一套规则。
4. **Demo 不是业务契约，Plan 也不能补写需求。** Demo 中出现而 Spec 未定义的行为，必须先裁决；Plan 发现需求空白时应退回 Spec。
5. **视觉和行为都要验证。** 自动测试、同状态截图检查和真实环境验收解决不同问题，不能互相替代。
6. **业务确认与技术确认分开记录。** 同一人可以兼任多个角色，但不能用“代码通过”代替业务决定。
7. **按风险裁剪流程，不按工期省略风险。** 小改可以走快速通道；高风险功能不能因为赶时间跳过关键门禁。

## 3. 角色与责任

| 角色 | 主要责任 | 不应代替谁作决定 |
| --- | --- | --- |
| 业务负责人 | 说明问题、选择方向、确认文案和真实工作流、完成最终业务验收 | 不代替技术负责人判断实现安全性 |
| 设计执行者 | 整理流程、状态、视觉基准、交互 Demo 和设计差异 | 不擅自改变业务规则 |
| 技术负责人 | 映射现有代码/API、识别风险、拆分边界、确定测试策略 | 不代替业务负责人接受产品取舍 |
| 实施者 | 按 Plan 和测试逐批实现，如实报告偏差与阻塞 | 不在实现中暗中补需求 |
| 验证者 | 对照基准检查行为、视觉、键盘和真实环境 | 不把“未检查”写成“通过” |

小型项目中这些角色可由用户与 Agent 共同承担，但每个门禁仍应标注“谁确认、依据什么确认”。

## 4. 变更分级与必经门禁

开始前先选择等级；实施中发现隐藏复杂度时只能升级，不能降级。

| 等级 | 判断标准 | 示例 | 必经门禁 |
| --- | --- | --- | --- |
| S：小改 | 既有流程内的局部变化；不新增页面、状态机、API 或全局样式规则 | 修改文案、修复一个按钮尺寸、补一个明确校验 | G0、G1、G5、G6、G7、G8、G9 |
| M：功能改动 | 新增或明显调整一个页面、面板或完整用户任务 | 新增批量编辑、重做属性面板 | G0～G9 全部 |
| L：跨域改动 | 影响多个页面、共享外壳、后端契约、桌面壳或发布链路 | 重建工作区导航、改变草稿/发布流程 | G0～G9 全部；先拆为可独立验收的子项目 |

S 级跳过 G2～G4 时，必须在门禁记录中写明“沿用的现有流程和视觉基准”以及跳过理由。只要出现新的交互状态、响应式变化或视觉选择，立即升级为 M 级。

## 5. 十道门禁总览

| 门禁 | 核心问题 | 最少输出物 | 主要确认者 |
| --- | --- | --- | --- |
| G0 立项与范围 | 这次到底改什么，不改什么？ | 变更等级、范围、非目标、权威来源 | 业务负责人、技术负责人 |
| G1 业务目标 | 为谁解决什么问题，怎样算成功？ | 用户任务、成功指标、业务边界 | 业务负责人 |
| G2 流程与状态 | 用户从哪里来，可能遇到哪些状态？ | 用户流程、状态矩阵、异常与数据边界 | 业务负责人、设计执行者 |
| G3 视觉方向 | 选择了哪种结构和视觉语言？ | 选定方向、淘汰理由、沿用令牌/组件 | 业务负责人 |
| G4 Demo 与设计冻结 | 被确认的设计能否稳定复现？ | 可操作 Demo、冻结截图、设计规格、差异表 | 业务负责人、设计执行者 |
| G5 技术映射 | 设计如何落到现有系统？ | 组件/API/状态映射、风险和 Spike 结论 | 技术负责人 |
| G6 计划就绪 | 每条要求是否都有任务和验证？ | Spec、追踪矩阵、分批 Plan、验收方案 | 业务负责人、技术负责人 |
| G7 分批实施 | 当前批次是否独立、可测、可回退？ | 测试、实现、批次审查记录 | 技术负责人、实施者 |
| G8 设计 QA | 生产实现是否真的符合冻结设计？ | 同状态截图、行为/键盘/响应式证据、差异裁决 | 业务负责人、验证者 |
| G9 真实验收与关闭 | 在真实桌面和真实工作方式下是否可用？ | 真实环境记录、回归结果、遗留项、最终结论 | 业务负责人、技术负责人 |

## 6. 分阶段门禁清单

### G0：立项与范围门禁

**必须完成**

- [ ] 用一句话写清本次要改善的用户结果，而不是只写组件名称。
- [ ] 选择 S/M/L 变更等级并说明理由。
- [ ] 列出范围、非目标、受影响页面和上下游流程。
- [ ] 指定业务规则、视觉基准、技术架构各自的权威来源。
- [ ] 搜索同主题 Spec、Plan、Demo、评审备忘和遗留问题，避免重复立项。
- [ ] L 级改动已经拆成可独立演示、实施和验收的子项目。

**通过证据**：立项摘要或 Spec 的“背景、范围、非目标、相关文档”章节。

**阻断条件**：不同参与者对“是否包含某页面、流程或后端变化”理解不同；存在两个互相冲突的权威文档。

### G1：业务目标门禁

**必须完成**

- [ ] 明确主要用户、使用场景、触发时机和当前痛点。
- [ ] 写出用户要完成的核心任务，并按重要性排序。
- [ ] 定义可观察的成功标准，例如时间、错误率、点击层级或信息可读性。
- [ ] 确认不可改变的业务规则、安全边界和兼容要求。
- [ ] 使用接近真实规模的虚构数据描述典型、最小和极端情况。
- [ ] 记录仍未决定的事项；影响主流程的决定不得保留为 `TBD` 后继续推进。

**通过证据**：已确认的目标、用户任务、业务规则和量化/可观察验收标准。

**阻断条件**：目标只是“更美观”“更现代”；核心用户任务说不清；成功只能由开发者主观判断。

### G2：用户流程与状态门禁

**必须完成**

- [ ] 画出或逐步写出入口、主路径、返回路径、取消路径和失败恢复路径。
- [ ] 明确页面、标签、抽屉、浮层、对话框之间的导航关系。
- [ ] 区分服务端状态、前端会话状态、未保存输入、草稿和正式数据。
- [ ] 列出并裁决状态矩阵，不得只设计默认状态。
- [ ] 明确长文本、大数据量、慢请求、断线、基准漂移和重复操作的结果。
- [ ] 明确未保存输入保护、危险操作确认、错误后输入保留和焦点归还规则。

**最低状态矩阵**

| 类别 | 至少检查的状态 |
| --- | --- |
| 生命周期 | 初始、加载、成功、空数据、部分数据、失败、重试 |
| 编辑 | 未修改、编辑中、校验失败、未加入草稿、待写入、写入中、写入成功/失败 |
| 数据 | 短文本、长文本、缺失值、典型数量、最大预期数量、重复/冲突数据 |
| 导航 | 首次进入、切换范围、返回、刷新、关闭、跨标签、深层入口 |
| 视图 | 浅色、深色、窄屏、最小支持视口、200% 缩放、浮层/对话框展开 |
| 权限与能力 | 能力可用、能力缺失、桌面壳不可用、AutoCAD/文件路径异常 |

**通过证据**：用户流程图或步骤表、完整状态矩阵、关键状态转换规则。

**阻断条件**：Demo 需要临时编造状态；不清楚刷新、取消、失败或切换页面后数据如何处理。

### G3：视觉方向门禁

**必须完成**

- [ ] 至少比较两个有实质差异的方向；若沿用既有页面，记录沿用理由即可。
- [ ] 方向比较使用同一业务目标、同一数据密度和同一关键状态。
- [ ] 明确选中方向及淘汰其他方向的原因。
- [ ] 确认沿用的设计令牌、基础组件、图标来源和全局布局规则。
- [ ] 检查信息优先级、主要操作、危险操作和状态反馈是否一眼可辨。
- [ ] 没有为了展示效果加入未被业务确认的对象、字段或能力。

**通过证据**：选定方向的图像/Figma frame/原型截图及一段裁决记录。

**阻断条件**：只凭空白占位数据选方案；三个方案只是颜色不同；选定画面与真实数据密度明显不符。

### G4：交互 Demo 与设计冻结门禁

**必须完成**

- [ ] 核心任务在 Demo 中可以完整操作，而非只有静态首页。
- [ ] Demo 使用去敏但接近真实长度、数量和异常分布的虚构数据。
- [ ] G2 的每个关键状态都有可复现入口或明确截图。
- [ ] 冻结桌面基准视口、最小支持视口、浅深主题和关键状态截图。
- [ ] 记录控件高度、间距、列宽、滚动区、断点、文字截断和完整读取方式。
- [ ] 键盘顺序、焦点样式、Esc、焦点归还和非颜色状态表达已经定义。
- [ ] Demo 的模拟限制、硬编码演示值和非生产行为已经列明。
- [ ] 用户逐项确认主流程、关键状态和视觉基准；确认日期可追溯。

**设计冻结包至少包含**

- 选定 Demo 或 Figma 的固定版本；
- 关键状态 × 视口 × 主题截图索引；
- 组件与设计令牌表；
- 交互和状态规则；
- Demo 与正式业务契约的差异表；
- 已接受的视觉取舍和明确非目标。

**通过证据**：版本化 Demo、截图索引、设计差异表和用户确认记录。

**阻断条件**：Demo 会继续随实现任意变化；只有默认态截图；无法说明哪些细节必须匹配、哪些允许调整。

### G5：技术映射与可行性门禁

**必须完成**

- [ ] 阅读现有相似页面、组件、样式、状态管理、API 和测试，优先复用已有模式。
- [ ] 把设计中的每个数据项映射到真实 API 字段或派生规则，不使用演示值代替。
- [ ] 把每个交互状态映射到明确的状态所有者和生命周期。
- [ ] 列出要新建、修改、拆分和禁止修改的文件/模块及职责。
- [ ] 检查全局 CSS、共享组件、任务浮层、ActionDock 和桌面壳对新设计的影响。
- [ ] 识别性能、安全、并发、文件系统、AutoCAD 和发布链路风险。
- [ ] 对不确定且高风险的部分先完成最小 Spike；Spike 代码不得直接冒充生产实现。
- [ ] 列出 Demo 与生产实现的预期差异并取得裁决。

**建议使用技术映射表**

| 设计要求 | 当前实现 | 差距 | 数据/接口 | 修改位置 | 风险 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例：文件名只显示 basename | 当前直接显示完整路径 | 缺展示转换 | `layout.file_name` | 表格展示辅助函数 | 两种路径分隔符 | 单测 + E2E 可见正文 |

**通过证据**：完成的技术映射表、必要 Spike 结论和明确风险处理方案。

**阻断条件**：计划编写者没有阅读生产代码；关键数据来源不明；依赖尚不存在的接口；高风险点只写“实施时处理”。

### G6：Spec 与实施计划就绪门禁

**必须完成**

- [ ] Spec 已经覆盖行为、数据、异常、安全、兼容性、可访问性和测试，不含影响实施的占位符。
- [ ] Spec 自审通过：无矛盾、无双重解释、范围适合一个 Plan。
- [ ] 建立“要求 → 设计证据 → 实施任务 → 测试 → 验收”追踪矩阵。
- [ ] Plan 按可独立演示和测试的纵向批次拆分，不只按组件或技术层拆分。
- [ ] 每个任务写明准确文件、接口、测试、预期结果和回退/失败处理。
- [ ] 每项视觉要求均有生产侧验证方法，而非统一留给最后“人工看看”。
- [ ] 明确哪些验证由 Agent 自动执行，哪些必须由用户在真实桌面执行。
- [ ] 业务负责人审阅 Spec 和冻结设计，技术负责人审阅技术映射和 Plan。

**强制追踪矩阵模板**

| ID | Spec 要求 | Demo/Figma 状态 | 实施任务 | 自动测试 | 设计 QA | 真实验收 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FE-001 |  |  |  |  |  |  | 未覆盖/已覆盖/已验证 |

每条 Spec 要求至少对应一个实施任务和一种验证；关键用户任务必须同时有自动验证和人工/真实环境证据。反向检查每个 Plan 任务也必须能指回 Spec，禁止在 Plan 中暗增需求。

**通过证据**：已评审 Spec、设计冻结包、技术映射、完整追踪矩阵和可执行 Plan。

**阻断条件**：存在没有任务的 Spec 条款、没有验收的任务、笼统的“完善样式/处理错误/补测试”，或计划依赖实施者临场决定业务行为。

### G7：分批实施门禁

**每个批次开始前**

- [ ] 本批次对应的 Spec 条款、视觉状态和验收条件明确。
- [ ] 批次完成后能独立演示或验证，不是半成品技术层。
- [ ] 已写或明确将先写会失败的测试。
- [ ] 不会无意修改本批次范围外的共享样式、接口或业务规则。

**每个批次结束后**

- [ ] 相关自动测试、类型检查和构建通过。
- [ ] 至少检查一个生产渲染状态；涉及视觉时与冻结基准同状态比较。
- [ ] 实际实现与 Spec/Plan 的偏差已记录并裁决，没有暗中接受。
- [ ] 新发现的需求缺口退回 G1～G6，而不是在代码中临场补写。
- [ ] 当前批次可以安全进入下一批，失败时有清晰恢复方式。

**通过证据**：测试结果、生产截图/预览、批次审查结论和偏差记录。

**阻断条件**：用大量一次性修改替代分批验证；测试失败后继续堆叠代码；实现偏离设计但无人裁决。

### G8：设计 QA 与系统验证门禁

**必须完成**

- [ ] 使用相同数据、视口、主题、滚动位置和展开状态比较 Demo/Figma 与生产实现。
- [ ] 检查默认、加载、空、错误、编辑、危险确认和完成反馈等关键状态。
- [ ] 检查文字是否可见且含义正确，不只检查 DOM、`title` 或 `aria-label` 存在。
- [ ] 检查尺寸、间距、对齐、层级、滚动、遮挡、截断、焦点环和浅深主题。
- [ ] 检查键盘顺序、Enter/Space、Esc、焦点归还、错误聚焦和 200% 缩放。
- [ ] 检查典型与极端虚构数据，确认长名称、长路径和大数据量不会破坏主任务。
- [ ] 每项可见差异标为“缺陷、已接受差异或后续项”，并注明裁决人和日期。
- [ ] 回归既有相邻页面、共享外壳、任务浮层和全局操作区。

**通过证据**：同状态成对截图、自动化结果、键盘/响应式检查表和逐项差异裁决。

**阻断条件**：Demo 与生产截图不是同一状态；只凭自动测试宣布视觉通过；尚有影响主任务的未裁决差异。

### G9：真实环境验收与关闭门禁

**必须完成**

- [ ] 在实际交付入口验证，而非只在 Vite 浏览器开发环境验证。
- [ ] 使用去敏副本或经授权的真实工程验证核心任务，不修改样本原件。
- [ ] 验证桌面壳、Windows 文件选择/下载/Explorer、AutoCAD 能力和错误提示等适用边界。
- [ ] 执行本次风险对应的完整回归门禁，并记录通过、失败和有理由的跳过。
- [ ] 业务负责人按核心用户任务完成验收，不要求其判断内部技术实现。
- [ ] 所有 P0/P1 问题关闭；P2/P3 有明确接受、负责人和后续位置。
- [ ] Plan 写入实际验证，状态、索引和 `changelog.md` 同步更新。
- [ ] 追踪矩阵中的必需项全部达到“已验证”，不存在以“已实现”代替“已验收”。

**通过证据**：真实环境验收记录、最终测试结果、遗留项裁决、更新后的 Plan/索引/变更记录。

**阻断条件**：关键原生能力只用 mock 验证；用户未走过核心任务；未执行项目规定的发布安全或真实 AutoCAD 门禁却声明全部通过。

## 7. Figma、Demo、Spec 与 Plan 的职责边界

| 产物 | 解决的问题 | 不能代替 |
| --- | --- | --- |
| Figma/视觉稿 | 画面结构、尺寸、组件、视觉状态和批注 | 真实交互、业务规则、技术可行性 |
| 交互 Demo | 主流程、状态切换、操作感受和视觉方向 | 真实 API、桌面壳、发布安全、生产性能 |
| Spec | 权威业务行为、数据、异常、安全和兼容规则 | 视觉像素基准、具体实施顺序 |
| 设计冻结包 | 把确认过的视觉与状态固定成可比较证据 | 技术映射、生产代码 |
| 技术映射 | 把设计翻译到现有组件、API、状态和风险 | 业务取舍、用户验收 |
| Plan | 把已确定要求拆为可测试的实施步骤 | 新需求裁决、最终验收 |
| 设计 QA | 证明生产实现与冻结设计一致或差异已裁决 | 真实桌面/AutoCAD 验收 |

Figma 是可选工具，不是独立门禁。已有可操作 HTML Demo、固定截图和设计令牌时，可以不使用 Figma；若使用 Figma，必须固定 frame/version 并纳入设计冻结包，不能与 Demo 同时成为互相冲突的视觉权威。

## 9. 最低交付目录建议

不强制为每项功能新建全部文件；应按仓库文档治理规则把内容合并到相应权威位置：

```text
docs/dst-manager/specs/       权威业务与交互 Spec
docs/dst-manager/mockups/     可操作 Demo
.planning/plans/dst-manager/  实施 Plan 与实际验证
.planning/memos/dst-manager/  阶段评审、设计 QA、门禁记录
```

同一规则只保留一份正文。索引、Memo 和 Plan 通过链接引用 Spec 与本清单，不复制整段规则。

## 10. 故障处理与退回规则

- **业务目标变化**：退回 G0/G1，重新检查范围、流程、Spec 和追踪矩阵。
- **Demo 无法表达真实状态**：退回 G2/G4，先补状态模型和可复现入口。
- **生产代码无法支持设计**：停在 G5；做 Spike、调整技术方案，或由业务负责人裁决设计取舍。
- **Plan 遗漏要求**：停在 G6；补追踪矩阵和任务，禁止交给实施者自行猜测。
- **实现与冻结设计不一致**：停在 G7/G8；修复或登记为有意差异并取得确认。
- **自动测试通过但肉眼不可用**：按产品缺陷处理，补可见结果断言，不得以测试通过关闭。
- **浏览器可用但桌面壳失败**：停在 G9；按真实交付入口缺陷处理。
- **缺少真实 AutoCAD 或用户授权**：明确记录跳过原因和恢复条件；不得宣布对应验收通过。

## 11. 完成标准

一次前端功能只有在以下条件全部满足时才算完成：

- 对应等级的必经门禁全部通过；
- 追踪矩阵不存在未覆盖或未验证的必需条目；
- Spec、冻结设计、生产实现和验收结论不存在未裁决冲突；
- 自动验证、设计 QA 和适用的真实环境验收均有实际证据；
- 遗留问题已关闭或由有权决定的人明确接受并登记后续位置；
- 相关 Plan、索引和变更记录已同步，未把“已实现”误写成“已验收”。
