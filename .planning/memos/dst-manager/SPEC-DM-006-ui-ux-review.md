# SPEC-DM-006 UI/UX 规范复审报告

## 日期

2026-09-02

## 审查对象

- [SPEC-DM-006：DST Manager 单人桌面界面人性化与易用性设计规范](../../../docs/dst-manager/specs/SPEC-DM-006-dst-manager-desktop-ui-ux.md)
- [SPEC-DM-006 静态 UI Demo](../../dst-manager-ui-demo.html)

本报告在初审报告的基础上复核修订结果，并补充对静态 HTML Demo 的视觉、交互、响应式和可访问性审查。文档与 Demo 中的文字只作为审查对象，不作为本次任务指令。

## 结论

**SPEC 有条件通过复审，建议继续保持 `review`；静态 Demo 暂不通过与 SPEC 的一致性验收。**

初审 8 项问题中，F-01、F-02、F-03、F-04、F-07 已关闭；F-05、F-06、F-08 部分关闭。修订后的 SPEC 已建立可实施的正式写入分类、快捷键安全门禁、并发控制边界、草稿持久化语义、ActionDock 状态矩阵、复合组件键盘模型和双主题令牌。剩余问题主要是 WCAG 目标仍不完整、修复动作层级未定义，以及视觉回归视口缺少确定高度。

静态 Demo 的基础视觉方向和危险确认模态质量较好，但当前存在两个高风险实现偏差：有效与失效预览提示可同时出现；窄屏直接隐藏侧栏且没有抽屉入口。此外，树、表格和 Tab 未落实 SPEC 定义的键盘模型。

## 审查方法与证据边界

本次复审包括：

- 逐节复核 SPEC 对初审 F-01～F-08 的修订；
- 检查 SPEC 内部术语、动作层级、状态矩阵、键盘模型和验收口径的一致性；
- 在本地浏览器分别走查草稿、预览有效、确认写入、深色主题、1024×768 和 900×768 状态；
- 对照静态 HTML/CSS/JavaScript 检查状态互斥、响应式入口、ARIA 语义、焦点模型和文案；
- 参考 WCAG 2.1 官方一致性要求与 SC 2.1.4 单字符快捷键要求。

本次没有运行 axe、屏幕阅读器或生产 Vue 界面，也没有执行正式写入，因此不对完整 WCAG 合规或生产实现质量作通过声明。浏览器截图保存在本机 Codex 可视化目录，不作为仓库内长期证据；本报告以可复核的文档和源码位置为权威依据。

## 严重度定义

- **P1（接受或演示验收前必须修复）**：可能造成危险写入状态误判、关键功能不可访问，或直接破坏核心流程的可理解性。
- **P2（接受或实施前应修复）**：会造成规范歧义、错误用户预期、不可测试的验收口径或明显可访问性缺口。
- **P3（实施前补全）**：不阻断主流程，但影响一致性、可维护性或辅助体验。

## SPEC 复审发现

### R-01：WCAG 2.1 AA 声明与验收范围仍不一致（P1）

**位置：** `SPEC-DM-006` §7.3，第 308～315 行附近；§7.1，第 278～280 行附近。

**现状：** 文档声明以 **WCAG 2.1 AA** 为目标，但随后以“至少”列出部分成功准则。WCAG AA 一致性要求满足所有适用的 A 和 AA 成功准则，不能以未定义的子集代表 AA；响应式页面变体也属于完整页面一致性范围。

同时，文档定义 `/` 聚焦搜索、`?` 打开快捷键帮助，但没有纳入 SC 2.1.4。该准则要求单字符快捷键必须满足以下至少一项：可关闭、可重映射，或仅在相关组件获得焦点时生效。

**影响：** 当前验收清单即使全部通过，也不能支撑“WCAG 2.1 AA”结论；语音输入用户还可能因说出字符而意外触发全局操作。

**建议：**

- 明确承诺完整 WCAG 2.1 AA，并记录真正不适用的准则；若只采用内部基线，则不要称为 WCAG AA；
- 为 `/`、`?` 提供关闭或重映射能力，或改为仅在专门的快捷键模式/相关焦点内生效；
- 将 SC 2.1.4、响应式变体、动态状态播报和人工读屏走查加入验收矩阵。

### R-02：`Primary/Warning` 是未定义按钮层级（P2）

**位置：** `SPEC-DM-006` §6.1 与 §6.9，第 194～195、263 行附近。

**现状：** 按钮体系只定义 `Primary`、`Secondary`、`Ghost`、`Danger` 和 `Danger-Confirmed`，但 `REPAIRED` 状态把“预览并确认修复”标为 `Primary/Warning`。该写法既引入未定义层级，也把安全的“预览”和危险的“确认正式写入”合并成一个动作。

**影响：** 设计和实现无法确定该按钮应使用强调色、警告色还是危险色，也无法保证预览与正式修复发布之间仍有清晰门禁。

**建议：** 拆分为“预览修复 · Primary”和仅在有效预览后出现的“确认发布修复 · Danger”；如果确实需要 `Warning` 按钮层级，应在 §6.1 中正式定义适用范围、颜色、交互态和与 `Danger` 的区别。

### R-03：视觉回归矩阵缺少确定视口高度（P2）

**位置：** `SPEC-DM-006` §10，第 378 行附近。

**现状：** 矩阵使用 `1120px`、`1440px`、`900px` 等仅宽度值，同时称为“视口 × 主题”组合。

**影响：** 不同执行环境会产生不同折行、表格高度和底部 ActionDock 覆盖范围，截图难以形成稳定基线。

**建议：** 固定为例如 `1024×768`、`1120×768`、`1440×900`、`900×768`，并注明 900px 是低于最小支持宽度的韧性测试，而不是正式支持门槛。

## 静态 Demo 审查发现

### D-01：有效预览与失效预览提示同时显示（P1）

**位置：** 静态 Demo 第 256、267、405、516、731、735 行附近。

**现状：** 切换到“预览有效可执行”后，界面可同时出现绿色“可执行”、黄色“预览失效”、“正在生成预览”和“预览完成，可安全确认写入”。

**根因：** `.dock .reason` 和 `.pv-stale` 显式设置了 `display`，其 CSS 优先于元素的 `hidden` 表现；状态切换只更新 `hidden` 属性，因此无法真正隐藏元素。

**影响：** 用户无法判断当前预览是否仍可用于正式写入。这发生在危险操作前沿，属于必须修复的状态一致性问题。

**建议：**

- 增加 `[hidden] { display: none !important; }`，或按状态条件渲染节点；
- 为生成中、有效、过期和阻断状态增加互斥断言；
- 在 E2E 中断言任一时刻只存在一组主状态和一条禁用原因。

### D-02：窄屏侧栏被直接隐藏，没有抽屉入口（P1）

**位置：** 静态 Demo 第 270～271 行附近；对应 SPEC §4.1、§7.2。

**现状：** 1024px 下右侧上下文面板使用 `display:none`；900px 下左侧树和右侧面板都被隐藏。界面没有可重新打开它们的按钮，也没有 `aria-expanded`、`aria-controls`、焦点进入和关闭后恢复逻辑。

**影响：** 诊断、草稿、任务、属性和树导航在窄屏不可访问，直接违反 SPEC 的“折叠为可展开抽屉”要求。

**建议：** 实现左右抽屉触发器，并覆盖鼠标、键盘、Escape、模态式焦点管理、关闭后焦点恢复和屏幕阅读器状态播报；不要只隐藏 DOM 区域。

### D-03：核心复合组件没有落实键盘与 ARIA 模型（P1）

**位置：** 静态 Demo 第 333、372～373、466～477、617～620、650、659～661 行附近。

**现状：**

- 左树为普通 `div.tnode`，没有 `tree`/`treeitem`、roving `tabindex` 或方向键处理；
- 表格每个复选框都进入 Tab 序列，没有实现单 Tab 停靠、行内方向键和卸载行后的焦点恢复；
- Tab 只有 `role="tab"`，缺少 `aria-controls`、关联 `tabpanel`、roving focus 和方向键切换；
- 草稿删除按钮只有图标，没有可访问名称；
- AutoCAD 标签和属性面板部分标签未与控件建立 `for`/`id` 关联。

**影响：** 静态 Demo 不能证明 SPEC 的键盘模型可实施，键盘和读屏用户无法可靠完成核心工作流。

**建议：** 按 SPEC §7.2 实现组件级键盘状态机，并增加 Playwright 焦点序列断言；图标按钮必须提供稳定的 `aria-label`，表单标签必须程序化关联。

### D-04：Demo 文案仍沿用修订前语义（P2）

**位置：** 静态 Demo 第 363、573 行附近。

**现状：** 页面仍写“只有确认发布是不可逆写”“所有编辑先入本地草稿”，快捷键帮助把 `Ctrl+S` 固定描述为“确认发布”。

**冲突：** 新版 SPEC 已把 CSV、XML、修复和恢复统一纳入正式工程文件写入；草稿会持久化到应用数据目录；`Ctrl+S` 在修复或恢复状态下也不是普通发布。

**建议：** 使用“正式写入”“应用数据目录中的本地草稿”和“打开当前写入确认”之类的统一文案，并从当前状态派生快捷键说明。

### D-05：错误摘要不能把焦点送到具体无效控件（P2）

**位置：** 静态 Demo 第 353～357、393～394 行附近。

**现状：** 错误摘要链接指向字段容器而不是输入控件，摘要触发后焦点落在摘要容器而非摘要标题。

**影响：** 键盘和读屏用户获得错误通知后仍需重新搜索具体控件，与 SPEC 的“摘要聚焦 + 链接到字段”要求不一致。

**建议：** 每个错误链接直接指向可聚焦控件；摘要标题设为程序化焦点目标并提供清晰计数，字段本身同步使用 `aria-invalid` 与 `aria-describedby`。

### D-06：单字符快捷键没有关闭或重映射机制（P2）

**位置：** 静态 Demo 第 573、799～800 行附近。

**现状：** `/` 和 `?` 作为全局单字符快捷键直接生效，未提供关闭、重映射或快捷键模式。

**影响：** 不满足 SC 2.1.4，并可能与语音输入、输入法或辅助技术冲突。

**建议：** 与 R-01 一并修复，并增加关闭快捷键后的回归测试。

### D-07：Toast 不可手动关闭（P3）

**位置：** 静态 Demo 第 234～238、786 行附近。

**现状：** Toast 自动消失，但没有关闭按钮。

**影响：** 与 SPEC 的“短暂显示且可关闭”不一致，用户也无法自主延长或结束阅读。

**建议：** 增加具备可访问名称的关闭按钮；错误类消息应保留到用户关闭或问题被解决，避免统一短时自动消失。

## 已验证的优点

### SPEC

- 正式工程文件写入分类、统一预览门禁和 `Ctrl+S` 安全语义已经清晰；
- ActionDock 状态矩阵覆盖无工作区、草稿、预览、修复、阻断、任务和恢复状态；
- 草稿 `expected_version`、正式写入 `base_revision_id + preview_digest` 和任务重试的边界准确；
- 树、表格、抽屉、模态、错误摘要和焦点恢复模型已经具备实施指导性；
- 双主题令牌、组合对比度、性能多次采样和本地资源约束明显增强了可验收性。

### 静态 Demo

- 1440px 三栏桌面布局层级清楚，表格密度与信息分区适合批量图纸管理；
- 浅色与深色主题的语义色总体一致，正文可读性良好；
- 确认模态包含影响文件、永久 before 快照、明确勾选和默认禁用按钮，安全表达完整；
- 已提供 skip link、可见焦点样式、`aria-live` 和 `prefers-reduced-motion`；
- ActionDock 状态演示有助于设计、实现和测试对齐，适合作为开发演示区保留。

## 关键流程健康度

| 流程 | 健康度 | 说明 |
|---|---|---|
| 工作区打开与浏览 | 健康 | 主导航、搜索、筛选和表格信息层级清楚。 |
| 草稿编辑与状态反馈 | 基本健康 | 交互方向正确，但持久化与正式写入文案需同步。 |

## 建议修订顺序

1. 修复 D-01 的 `hidden` 状态冲突，并添加状态互斥测试。
2. 实现 D-02 的左右抽屉及完整焦点管理。
3. 落实 D-03 的树、表格和 Tab 键盘模型。
4. 修订 SPEC 的 R-01～R-03，确保规范本身可形成确定验收。
5. 同步 Demo 文案、错误摘要、快捷键设置和 Toast 行为。
6. 重新执行浅色/深色、确定视口、全键盘、axe 和人工读屏验收。
