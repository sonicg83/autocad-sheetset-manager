01

结论

技术上完全可行，而且不需要"重建视口"这条最难的路。视口丢失是当前替换方式造成的，不是 AutoCAD 的限制。关键在于把布局的两个身份解耦——它既是视口的宿主，又是「标准（图框 + 字段 + 页面设置）」的载体。

首要发现

图纸集字段只在布局中求值，因此图框、字段、视口必须同处宿主 DWG 的同一个布局内。这条约束否决了"图框改为外部参照"的整条路线，也把方案空间收缩到四个候选。

意外收获

legacy 的 SetViews / SetViewPort 就是"把视口存成可复用数据再恢复"的完整实现，用的全是 AutoCAD 原生结构（命名视图 + 图层状态），不是自研偏方。

需要澄清

Callout Block（标注块）与"保视口"是两件事。它解决的是图与图之间的交叉引用自动更新，不能用来解视口问题；但值得作为独立能力立项。

02

根因：删除布局 → 视口随布局消失

现状的替换方式是"删掉全部布局 → 从模板 DWG 重新导入布局"。浮动视口（AcDbViewport）是布局的图纸空间 BlockTableRecord 内的实体，布局被删除，视口连同视图参数、比例、非矩形剪裁、锁定、视口级图层覆盖（VP 冻结 / VP 颜色）一起消失。

03

决定性硬约束：字段只在布局中求值

推论

图框 + 字段 + 视口，三者必须同处宿主 DWG 的同一个布局内。

这不是"xref 不行"这么窄——而是"凡是不能在布局求值上下文中出现的东西，都不能承载图纸集字段"。

来源与原文依据
事实来源
图纸集字段放在布局里正常、放到模型空间失效Autodesk 论坛、Reddit 同题（原话："that field only works when the block is in paper space"）
xref 图框拿不到字段；官方替代方案是"图框可外部参照，但标题栏数据要以文字存在每一张图纸里"Autodesk Blog：Automate Title Block Data

Autodesk 官方限制

"Every layout viewport can have its own set of layer overrides but they cannot be copied, even in the same layout. Solution: Use layer states…"

05

legacy 资产：SetViews / SetViewPort

仓库 legacy/plugin/ 下（本地私有，不进入公开仓库）的两个历史插件，读完源码后确认：它们就是"把视口保存为可复用数据并恢复"的完整实现，用到的机制全部是 AutoCAD 原生结构。

独立印证 · 这不是自研黑科技

AutoCAD VIEW 命令创建模型视图时有「保存图层快照（Save layer snapshot with view）」选项，官方说明为：捕获当前图层状态，包括 ON/OFF、Freeze/THAW、LOCK 及图层颜色等属性，恢复视图时一并恢复。

ViewTableRecord.LayerState 就是它 —— legacy 只是把同一件事编程化了。这意味着这些数据在纯 AutoCAD 里可见、可编辑、可复用，对"可审计"的定位非常契合。

现代化必须改造的 7 个点

#legacy 现状必改原因

06

批量提取、顺序与朝向

能否用“提取某图层全部封闭多边形”替代逐个人工拾取？能，但顺序不能靠算法猜——必须变成项目级显式声明 + 一次性建序 + N 次非交互复用。

已确认的两条现实约束（2026-10-01）
  • 图框矩形一般不带标识：矩形内没有图号属性 / 文字，图框块名也不含图号 ⇒「矩形自带标识」不能作为默认路径。
  • 顺序与工程类型相关：线性工程沿一条曲线（道路中心线等）铺设，顺序 = 沿中心线的推进顺序（里程 / 桩号序）；非线性工程按设计者喜好排布 ⇒ 无通用几何规则。
关键结论：先把“顺序”的语义还原出来

拾取顺序的唯一产物是编号，编号被写进 ViewTableRecord.Name；恢复侧用「布局名首段数字 ↔ 视图名数字」对齐。所以拾取顺序承载的是「这个矩形属于哪张图」，不是几何次序。

⇒ 几何排序只能给出「第 k 个」，而恢复需要的是图号；二者等价依赖「布局顺序 == 矩形几何顺序」这条隐含假设，必须显式化为可校验项。
⇒ 「非交互」的正确形态 = 一次建序 + N 次非交互复用（换阶段反复发生，建序只发生一次）。

三档排序策略（由项目 / 标准显式声明）

模式适用排序键自动化程度
linear线性工程：图框沿中心线铺设（含旋转对齐）矩形中心投影到中心线的里程参数全自动
grid非线性但排布规整：从左到右 / 从上到下 / 多排AABB 分带聚类 → 带内从左到右自动 + 预览确认
manual任意排布、蛇形、随意摆放已持久化的顺序表一次性交互建序，之后全非交互
linear · 沿中心线里程排序
  1. 取约定图层上的中心线（LWPOLYLINE / SPLINE / ARC 或多段链）
  2. nearest = curve.GetClosestPointTo(c, false)
  3. station = curve.GetDistanceAtParameter(curve.GetParameterAtPoint(nearest))
  4. 按 station 升序 ⇒ 里程序，与图号顺序天然一致

多条中心线时先按「离哪条最近」分组，组内按里程排，组间仍需外部清单；同里程并存多套图框（平面/纵断/横断）需第二排序键。

grid · 带容差的 reading order
  1. 取 AABB（扭转矩形用轴对齐包围盒，中心不变、区间稳定）
  2. tol = 0.5 × median(高度)
  3. 按 cy 降序聚类，差 ≤ tol 视为同带
  4. 带内按 cx 升序
  5. 行 / 列方向作为参数

tie-breaker 用 cx → cy → 面积，绝不能用句柄（句柄随编辑变化，两次运行结果会不一致）。

为什么 linear 必须有：grid 能覆盖「从左到右 / 从上到下 / 多排从左到右」这类 reading order 变体，但图框旋转对齐中心线时任何行列分带法都会失效；真正需要 manual 的是随意摆放与蛇形排布（第一行左→右、第二行右→左）——后者 reading order 必然判错。SetViews 的交互形态在「建序」这一次性场景下反而最优：人拾取时能立刻看到选中的是哪个图框。

顺序表与几何指纹（可恢复性的核心）

只把编号写进 ViewTableRecord.Name 不够：图被增删改、矩形数量变化时会静默错配（把 A 图的视口内容还原到 B 图）。

字段用途
view_number（= 图号）写在 ViewTableRecord.Name，恢复侧的对齐键
frame_fingerprint
中心 + 宽高 + 扭转（或 AABB 规范化哈希）		检测「图框被移动 / 替换」
frame_count（捕获时的矩形总数）数量不符即阻断
order_mode + 策略参数复现排序前提（中心线图层、行 / 列方向）
恢复时的双向校验（无标识下唯一的错配防线）
  • 每个命名视图反算模型范围 → 必须恰好落在一个矩形内
  • 每个矩形 → 必须恰好被一个视图覆盖（双射）
  • 矩形总数 == frame_count
  • 任一不符 → 报稳定诊断码并提示重新建序，绝不静默按顺序硬配

再叠加「从已有视口反推」（第 5 节改造项 7）作为第三条独立来源，可进一步降低错配概率。

命令形态（两步分离，便于预览与审计）

① DstListViewFrames <图层名> → 只读枚举封闭多边形，输出 JSON： { handle, aabb{cx,cy,w,h}, center, width, height, twist, area } （不做业务排序、不写库；可选附带 order_key 供预览） ② DstCreateViews <映射 JSON> → 按 { view_number → frame_handle | frame_fingerprint } 建命名视图， 写入 order_mode 元数据；写完回读做双向校验

排序与配对决策全部留在 Python 领域层（纯函数、可单测、可预览、可回滚），插件只做 CAD 数据库操作。

第三个自由度：朝向（UCS 依赖）

用户补充（2026-10-01）

在 SetViews 选择矩形框之前，需人工以矩形框为基准设置 UCS（底边为 X、高为 Y、X 正向朝着序号增加的方向）；只要矩形框不平行，每次都要重设 UCS。

⇒ 朝向的唯一输入源就是这个人工 UCS。若批量化只解决顺序、朝向仍靠人工设 UCS，则「非交互」目标并未真正达成。
⇒ 关键：自由度 ②「X 正向」恰恰就是「顺序」决定的——朝向与顺序是同一件事的两面。

自由度 ① 底边方向

矩形的「右」朝哪（对应矩形自身坐标系的 X 轴）。SetViews 用 db.Ucsxdir / Ucsydir 推导 TwistAngle，取的就是这个。

自由度 ② X 正向

沿底边的两个方向里选一个（指向「下一张图」的那个）。这一项可由排序结果的增量自动倒推。

AutoCAD 坐标系体系与各字段归属

名称定义要点谁在用
WCS世界坐标系，永不变；.NET API 未特别说明的点均按 WCSViewDirection、ViewTarget、模型 / 图纸空间实体坐标
UCS用户坐标系，工作用命令行输入输出；每视口保存的 Ucs + UcsPerViewport(UCSVP)
OCS / ECS对象坐标系，由实体自身拉伸方向定义部分实体属性（Polyline2d 等）
DCS显示坐标系：原点 = TARGET（视图目标点），Z 轴 = 视线方向；「视口永远是它自己 DCS 的正投影」ViewCenter / ViewHeight、AbstractViewTableRecord.CenterPoint / Height / Width
PSDCS图纸空间 DCS，只能与某个模型空间视口的 DCS 互转，本质是 2D 相似变换（可求比例）图纸空间 ↔ 视口 的位置 / 比例换算
两个推论
  • legacy 的「逐字段直接拷贝」是成立的：VP.ViewCenter = VR.CenterPoint 两侧的 DCS 由同样三个量（target / viewDirection / twist）定义，属同构坐标系，不是巧合。
  • twist / DVIEW 的「视图旋转」语义容易与直觉相反（官方专文 Objects in a Layout Viewport Appear Rotated Even Though They Look Correct in Model Space），任何手算都必须实测标定。
关键简化：ViewTarget = 矩形中心 ⇒ ViewCenter 恒为 (0,0)

因为 DCS 的原点就是 TARGET。这把「要算的 DCS 映射」降级为「一个约定」。legacy 之所以要手算 DcsCenter = CT.TransformBy(Rotation(TwistAngle))，正是因为它没动 target（默认原点）。

即：先排好序，朝向由排序结果的增量方向倒推——用户手工设 UCS 的两个自由度均可自动求解。

消歧风险

若图框旋转 90° 摆放（纵向图幅），「最接近水平边」可能选中短边 ⇒ 必须用「矩形 W:H 与标准图幅长宽比匹配（含 90° 旋转）」做消歧校验；无法消歧时转 manual。

twist 符号必须实测标定

官方只说「绕视线、从屏幕前方看向后方、零角在 DCS 正 X 轴」，未给出符号约定；legacy 的 if (Ucsxdir.Y > 0) TwistAngle = 2π − angle 分支也无法从静态阅读判定正误（取决于 Vector2d.GetAngleTo 的确切取值区间）。因此：

做法 1（优先）

用 AutoCAD 自带入口，绕开手算。ObjectARX 全局函数 acedSetCurrentView(AcDbViewTableRecord*, AcDbViewport*) 把视图记录直接应用到某视口，DCS 换算由 AutoCAD 自己完成（可与 legacy 用 acedSetCurrentVPort 同一套 P/Invoke 手法处理，需实测可行性）。

做法 2

若必须手算：把符号收敛到一个纯函数，用回读闭环标定——设一次、读回 ViewCenter / ViewHeight / TwistAngle 与视口的模型空间范围，与矩形逐项比对；约定做成常量或首次标定。

做法 3

单位口径必须显式声明：CustomScale = 图纸单位 / 模型单位，与坐标系无关，但「图幅长度」的单位口径（模型为米、图纸为毫米）若弄错，1:1000 会差 1000 倍。

legacy 遗漏：UCS 存了但不会生效

Viewport.UcsPerViewport（UCSVP）的说明是「若为 true，则随该视口保存的 UCS 生效」。legacy 用 SetUcs(...) 存了 UCS，但恢复时既未设 UcsPerViewport，也未设 Ucs ⇒ 该 UCS 实际上不会被激活。这是上节「改造项 5」的精确落点。

view ↔ viewport：一台相机的比喻

矩形框只是「圈个范围」；view 记录的是一台相机的姿态——相机站在哪、朝哪看、镜头怎么转、取景框多大。viewport 就是「把这台相机架到图纸上的某个位置，并按什么比例成像」。

两个「中心点」不要弄混

CenterPoint 是「窗户画在图纸的哪块地方」；ViewCenter 是「从窗户往里看，看到的是模型哪块地方」。

  • 换纸空间位置 → 只改 CenterPoint
  • 平移看到的模型内容 → 只改 ViewCenter / ViewTarget
  • 换比例 → 改 CustomScale（其余联动）
反直觉点 + 免费自检

视口自己永远不转，转的是「里面的模型」。图纸上那个窗口永远是正的，斜的是窗口里面的图——所以「旋转视口」是错误说法，实际改的是 TwistAngle。

若 twist 设对，必然有：

Width / ViewWidth == Height / ViewHeight

适用范围（标定推演后修正）：该式只验证「图幅内框宽高比 == 声明视图宽高比」的自洽性（ViewWidth 是我们自己写进去的，两边必然等比例），能抓图幅 / 视口尺寸不自洽，但不能抓 twist 错误。

比例与单位口径

Scale = 图幅内框长（图纸单位） ÷ 视图宽 W（模型单位）
视口纸空间宽 = W × Scale　视口纸空间高 = H × Scale

CustomScale 与坐标系无关，但 单位口径必须显式声明：模型按米画、图纸按毫米出，口径搞反会让 1:1000 差 1000 倍，且不会报错、只是图错。

契约速览（附录 A，draft 待立项）

两个固定命令：读与写分离，排序与朝向决策全部在 Python 领域层
命令性质输入输出
DstListViewFrames只读视图框图层（+ 中心线图层 · order_mode）<dwg>.dst-viewframes.json：frames[*] 几何 + diagnostics；不排序、不写库
DstCreateViews受控写入<dwg>.dst-create-views.json：views[*] · u_cs · unit_basis · frame_count回执 JSON：created/updated/skipped + verify{bijection_ok, ratio_ok, readback}
取舍 1 · 指纹不能只存哈希

frame_key（浮点规范量）用于容差匹配，frame_hash（量化到 1e-6）仅作日志 / 审计 —— 只存哈希就无法区分「图框被动了 0.1mm」与「图框被换掉」。

取舍 2 · theta_min 模 π/2

指纹用「四边方向角对 π/2 取模后的最小值」，消除 90° 倍数与旋转方向歧义 ⇒ 「朝向设错」不被指纹掩盖，交由定向角点比对抓出（职责分离）。

取舍 3 · twist 是配置不是常量

u_cs = {convention, twist_sign, twist_offset, center_transform}；autocad_native 走 acedSetCurrentView 让 AutoCAD 自算 DCS。带 calibrated 溯源字段，双版本各自标定。

取舍 4 · fail-closed

插件不读不写 DST；JSON 只从 Manager 生成的固定路径读；任一校验失败则整体不写（不部分应用）；VIEW_RATIO_MISMATCH 与 VIEW_BIPOSECTION_FAILED 为阻断级。

twist 标定三判据（附录 B，V8）

标定样本：底边与 X 轴成 30°、200×100，中心 (1061.6025404, 2093.3012702)
判据通过条件抓什么 / 抓不到什么
A · 定向角点比对把 DCS 窗口四角 (±100, ±50) 按 target+twist 映回 WCS，逐个命中 P1–P4（容差 1e-6）唯一能把 twist 全部错误抓全的客观判据：+30° 命中；−30° 与 +120° 均不命中
B · 宽高比自洽Width / ViewWidth == Height / ViewHeight（本样本 = 2.0）只抓图幅 / 视口尺寸不自洽或 paper_height 算错；不抓朝向
C · 目视样本内水平文字 / 箭头在视口中水平可读最直观的入眼确认；歪 60° 即符号反
标定推演发现的坑：AABB 不能代替角点

w(θ) = W|cosθ| + H|sinθ| 对 θ 对称 ⇒ +30° 与 −30° 的反算包围盒完全相同（都是 223.2050808 × 186.6025404）。所以「反算包围盒相等」不能当作朝向正确的证据，必须比定向角点。

方案 3 详解：图签块重定义

用户已确认：标准包布局模板资产中的字段就是放在图签块（增强属性块）里的。这让方案 3 直接成立。

实现机制

步动作要点
1把标准资产的同名块定义克隆进目标 DB用 IdMapping 一并带入嵌套块、图层、线型、文字样式等依赖；避免交互式 -INSERT 重定义
2ATTSYNC <块名> 同步属性Tag 相同 → 保留实例已有值；新块多出的 Tag → 用 ATTDEF 的 Default（即字段）初始化；旧块多出的 Tag → 删除
3若图幅也变，另行 AcDbPlotSettings::copyFrom图幅 / 图纸尺寸 / 打印样式 / 打印区域属于 Layout，不属于块
4回读校验 + before/after 哈希走既有发布事务

能力边界（须写入 Spec）

能管
  • 图签 / 会签栏 / 图框边框（只要是块）
  • 图签里的字段（ATTDEF Default）
  • 图签内的静态内容（规范号、版本号、行数）
  • 嵌套子块（图框 → 内嵌图签）
不能管
  • 图幅、页面设置、打印样式（Layout.PlotSettings）
  • 布局里非块的散落实体（指北针、说明文字）
  • 视口本身（正因不碰它，才零风险）
  • 图号 / 图名等 DST 属性（本就该改 DST，无需换图）

五个必须写进设计的坑

坑 1

页面设置不跟着变。阶段变化若含 A1→A2，只换图签块会出现"框线换了、纸张还是旧的"→ 出图错。标准里必须把"图签块资产"与"页面设置参数"拆成两类。

坑 2

块重定义是全局的。同 DWG 内所有该块名的参照都会换。若同 DWG 要并存两种图签（封面 vs 图纸），必须用不同块名按角色区分。

坑 3

ATTSYNC 保留旧值 = 字段可能被"人工覆盖"吃掉。若有人改的是属性值而非定义默认值，ATTSYNC 会保留该旧值 → 字段丢失。设计里要加校验项。

坑 4

字段必须放在 ATTDEF 的 Default，不能放在实例的 Value。Autodesk 原文警告："NEVER insert a field in an attribute 'Value.'"这同时是对现有资产的体检项。

坑 5

动态块。重定义会整体替换定义（含参数与可见性状态），实例当前可见性状态可能被重置；若标准资产是动态块须专门验证。

收益

视口 100% 不动 · 布局 Handle 不变 → DST 完全不需要回填 · 字段本就自动求值 · 无序列化、最好测、最易审计。

08

Callout Block 辨析

先纠正一个常见误解

Callout Block（标注块）不是视图，也不是视口方案。它是"指路牌"块——典型内容是 见 3/A-402，用来引用别的图纸上的视图。它的价值在于"图与图之间的交叉引用自动更新"，而不是保住视口。

四个相邻但不同的概念

概念是什么存在哪谁创建
Model View
模型视图		模型空间的命名视图（VIEW 命令），可选带"保存图层快照"DWG 的 ViewTable（数据库级）设计人员 / legacy SetViews
Sheet View
图纸视图		把一个 Model View 放到某张图纸上的实例：编号、标题、类别 + 那个视口DST：AcSmSheet → AcSmSheetViews → AcSmSheetViewSSM 的"放置视图"
View Label Block
视图标签块		放置视图时自动插在图口左下角，显示该视图编号 / 标题 / 比例DST：AcSmSheetSet → AcSmAcDbBlockRecordReference propname="DefLabelBlk"
单数，只能挂一个		图纸集属性中指定
Callout Block
标注块		不是视图，是"指路牌"块：见 3/A-402，引用别的图纸上的视图DST：AcSmCalloutBlocks（复数）；或按视图类别挂 AcSmViewCategory → AcSmCalloutBlockReferences图纸集属性中指定（可多个）

关键机制：SheetSetPlaceholder 字段 —— 这就是"搞不明白"的症结

AutoCAD Field 对话框里有两个容易混淆的类别
字段类别符号行为
SheetSetCurrentSheetNumber
CurrentSheetTitle
CurrentSheetCustom…		与具体图纸绑定，插入即求值。图签块用这一种。
SheetSetPlaceholderSheetNumber
ViewNumber		不与任何图纸或图纸集绑定，是"槽位"；由 SSM 在插入时填入被引用视图的图号与视图号。Callout 块用这一种。

"Using the SheetSetPlaceholder field in your callout block enables you to define block attributes for fields that are not associated with any particular sheet or sheet set."

为什么必须这样设计：Callout 块是模板——造块时还不知道将来要指向哪张图，所以用占位符，由 SSM 插入时填值，并可选 Associate hyperlink（点击标注块直接跳到被引用图纸并缩放到该视图）。

制作四要点
  1. 字段插在 BATTMAN → 属性定义 → Default，绝不能插在实例的 Value
  2. 属性定义 Preset = Yes（预设），插入时不提示输入
  3. 可选勾选 Associate hyperlink
  4. 块可存为独立 DWG，也可存为某 DWG / DWT 里的块定义；图纸集取用时两种模式：Select the drawing file as a block 或 Choose blocks in the drawing file
使用流程

SSM → Sheet Views 选项卡
→ 右键某个视图
→ Place Callout Block
→ 在图纸布局上点插入点

首次会提示先 Select Blocks，把 callout 块挂到图纸集属性上。

原生「Place View」不能用来解视口问题

SSM 的原生放置机制是：把 Model View 拖到图纸布局 → AutoCAD 把该图作为 XREF 附着到模型空间，按视图范围生成视口，并按比例设置缩放；放置时自动插入视图标签块。

硬伤 1

它会自带 XREF——为"模型文件 / 图纸文件分家"范式设计。而本项目是模型与布局同 DWG，用原生 Place View 就变成"自己 xref 自己"，或被迫拆成两个文件；而这正是第 3 节已否决的方向。

硬伤 2

它是交互式的（拖放 + 预览 + 右键选比例），accoreconsole 无人值守场景基本无法驱动。

硬伤 3

它只"加"视口，不"替换"——"换阶段时旧视口怎么办"这个核心问题一点没解。

本地真实样本实证

对本地 3 个真实工程 DST 做了元素普查（sample/project3 - copy/图纸集数据文件.xml、docs/shared/research/project1-dst-xml/project1_sheetset.xml、sheetset-fail.xml）。

DST 元素普查结果

结论 A

现有工程完全没用这套原生机制。容器骨架都在但全空 ⇒ "套图框出图"目前靠 legacy 的自研路线，与 DST 里这些容器无关；反证这块是真空。

结论 B

DST 里已有 设计阶段 自定义属性（样本值 初步设计）；图幅 是自定义图幅名（样本值 A3轨道，不是标准 A3）；出图比例 为 1:1000。⇒ 按阶段出图在属性层面已就绪，缺的只是图签 / 图幅 / 视口这一层的切换机制。

结论 C

DST contract 只登记了 7 类对象。AcSmCalloutBlocks、AcSmViewCategories、AcSmViewCategory、AcSmCalloutBlockReferences、AcSmAcDbBlockRecordReference 全部未登记，目前靠"未知元素宽容保留"。⇒ 要做 callout / label block，第一步必须先把这些纳入 contract registry。

决策与下一步

决策树：阶段差异在哪一层

  • A. 只是图纸集属性值不同（图号 / 图名 / 项目名）？
    • → 不动布局：改 DST 属性，字段自动求值（已有能力）
  • B. 图签样式 / 图签栏 / 规范号不同，图幅与图号不变？
    • → 方案 3：换同名块定义 + ATTSYNC（视口零风险）推荐
    • → 备选：布局整体替换 + 视口快照恢复
  • C. 图幅也变（A1→A2），或图号 / 图名随阶段变（本质是另一套图纸）？
    • → 必须动布局：方案 3 + PlotSettings，需要重排视口时叠加 方案 1
    • → 或 多布局 / 多阶段并存（图号变了就不可能"同一张图纸换皮"）
