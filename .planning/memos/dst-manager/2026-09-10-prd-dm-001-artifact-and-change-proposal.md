## 事实

### 一句话定位

两个概念服务于同一条边界原则（PRD §8.1）：**扩展永远不写正式工程文件，写入权 100% 留在宿主安全内核**。扩展对工程只有两种表达途径——「我想产出什么」和「我想改什么」。

| 概念 | 定位 | 通俗类比 |
| --- | --- | --- |
| `Change Proposal` | 扩展「想改工程」时递交的申请书 | 报销单：员工只能填单，钱由财务（宿主）付 |
| `Artifact` | 扩展「产出了什么」的成果登记 | 打印出的报表：可丢弃重打，账本本身没变 |

### `Change Proposal`（候选变更提案）

**是什么**（EXT-005）：扩展提出的工程变更必须是**结构化、可校验、带来源扩展和基准修订**的候选变更。关键在「结构化」——不是一段 XML、不是一条 SCR 命令、不是一句 Shell，而是宿主能读懂、能校验、能翻译成既有受控命令的数据对象。

**递交后走什么链路**：与人工操作完全相同的既有链路。

```
扩展提交 Proposal
  → 宿主统一预览（业务变化 / 受影响文件 / 是否需要 CAD / 风险 / 扩展来源）
  → 用户确认
  → 基准修订校验
  → 锁 + 暂存 + CAD 执行 + 验证
  → 整批发布（永久 before 快照 + 发布日志）
  → 任一步失败则整批回滚到发布前状态
```

EXT-005 明确：Proposal 被拒绝、验证失败或发布失败时，**正式工程保持发布前状态**。

**失效条件**（EXT-005）：基准漂移、能力变化、扩展停用、输入变化——四者任一发生，旧 Proposal 作废，须重新生成。

**实例一（连接器同步元数据）**：PLM 系统把 A-101 图纸的「专业」字段改为「结构」。连接器不给宿主发写请求，而是提交：

```
Change Proposal
  来源扩展：plm-connector v1.2.0
  基准修订：revision_id = R-0042
  内容：[ { 文件: A-101.dwg, 属性: 专业, 旧值: 建筑, 新值: 结构 } ]
```

宿主预览提示「1 个属性变更，0 个文件新增，不需要 CAD」，用户确认后才走受控编辑发布。

**实例二（嵌入 DWG 编辑应用）**：用户在 sidecar 中改图并点了 sidecar 自己的「保存」。EXT-011 明确：**不以 sidecar 的「保存成功」代替宿主成功**。sidecar 返回「候选文件 + 哈希 + Change Proposal」，仍须排队走宿主的基准校验、CAD 验证、整批发布。

**谁绝不能提交 Proposal**：

- **受控 AutoCAD 作业扩展（EXT-008）**：采用「严格 Artifact-only 模型」，「作业永远不得提交 `Change Proposal`」。
- **首期图纸目录扩展**：SPEC-DM-012 §42 把「产生 `Change Proposal`」明确列入非目标。

### `Artifact`（成果物）

**是什么**（EXT-006）：目录表、报告、PDF、派生 DWG、归档包、ZIP、manifest、校验和、缩略图和交换文件统一登记为 `Artifact`。首字母大写的 `Artifact` 是 DST Manager 的专有类型名，不是泛指「构建产物」。

**最核心的一条**：EXT-006 规定「Artifact 创建不自动成为工程修订；只有正式工程文件发生受控变化时才进入修订链路」。这是概念存在的理由——把「新生成了个文件」与「工程被改了」彻底分开，两种风险等级不共用一套流程（呼应 PRD §5 问题 3）。

**首期元数据字段**（ARCH-DM-006 §9.3）：

```text
artifact_id
extension_id / extension_version
workspace_id / source_revision_id     ← 该成果基于哪个修订
kind / media_type
management_relation = external
output_path / file_name
size_bytes / sha256
created_at
```

**`external` 与 `detached` 的区别**：

| 取值 | 含义 | 能否作为工作区打开 |
| --- | --- | --- |
| `external`（首期默认） | 文件由用户自行管理，应用不永久保存副本；路径缺失或哈希变化只派生 `MISSING`/`CHANGED` 状态，历史记录不伪装成当前可用文件 | 普通导出成果 |
| `detached` | 归档副本已解除 DST 关联（字段转纯文本、绑定外部参照） | **不能**，界面须明确说明不能再作为 DST Manager 工作区打开或回写 |

**实例一（图纸目录导出，首期唯一落地链路）**：用户点导出 → 原生「另存为」选目标（取消则不生成文件）→ 扩展在**临时目录**生成候选 XLSX → 宿主重开候选文件验证格式/工作表/表头/行数 → 原子替换 → 计算哈希并登记 Artifact。注意：**扩展自始至终不知道最终路径**，只拿到一次性、短时有效的 `save_grant_id`（ARCH-DM-006 §9.1）。

**实例二（打印 PDF）**：输出 PDF 与日志登记为 Artifact；宿主在执行前后校验输入副本哈希，打印作业若改动了输入副本直接判失败（EXT-008）。

**实例三（归档包）**：绑定外部参照并解除 DST 关联后标记为 `detached` Artifact，界面说明这是脱离管理的副本。

**实例四（失败情形）**：路径越界、磁盘不足、验证不过、只产出部分文件 → **不登记成功 Artifact**，只进诊断/操作日志（AC-005）。因此用户看到的「成功」Artifact 一定是完整且已校验的。

### 两者的关系

```
        扩展
       /     \
  Artifact   Change Proposal
  （产出）      （意图）
     ↓              ↓
  宿主登记      宿主预览 → 确认 → 基准 → 锁 → CAD → 验证 → 发布
  低风险            高风险（真的会改正式工程）
  可丢弃重生成       必须可回滚
  不进修订链路       进修订链路
```

PRD §7 另有一条易被忽略的规定：首期不提供扩展间直接互调 API，**扩展组合仅通过宿主能力、`Change Proposal` 与 `Artifact` 中介实现**。即 A 扩展不得直接调用 B 扩展，依赖关系必须经由宿主可见、可审计，单个扩展故障不牵连其他扩展。

## 临时结论

1. 两个概念本质是**同一安全边界在「产出侧」与「写入侧」的两个投影**，不是两个独立机制。理解任一个都应先接受 §8.1 的前提：最终裁决权不可被扩展替换。
2. **风险分级是设计主轴**：`Artifact` 低风险（可丢弃、可重生成、不进修订链路），`Change Proposal` 高风险（进正式工程、走全链路门禁、必须可回滚）。这解释了 EXT-008 为何被严格限定为 Artifact-only——受控 CAD 作业已经在动文件，再给提案权等于开后门。
3. 对后续 Spec/Plan 的直接影响：任何新扩展需求都应先判定属于「产出」还是「写入」，再选定流程；不得让同一功能同时走两套链路，也不得为图省事让产出侧夹带工程修改。

## 待跟进事项

1. **`Change Proposal` 尚无 Spec/ADR 背书**。2026-09-07 审查备忘已记录：`Change Proposal`、`Artifact` 均为本 PRD 首创概念，仓库中不存在记其取舍依据的 ADR/RFC/Research。`Artifact` 已在 ARCH-DM-006 首期设计中部分落地（有 `artifact_id`、`save_grant_id`、原子导出等具体契约）；`Change Proposal` 至本文撰写时仍只有 PRD 层面的边界原则，按 PRD §13 的演进顺序，预计要到「业务平台连接器」阶段才需要正式立项。
2. 因此当前引用 `Change Proposal` 时应表述为**已确立的边界原则**，不得表述为已实现的接口或已冻结的数据契约。
3. PRD §2 六项「已确认」决策的取舍依据缺失问题（2026-09-07 备忘 2 项重要问题之一）**仍未关闭**，与本备忘同源，处理时不应重复立项。
