## 二、重要问题

### 1. "已确认的方向"缺乏决策出处（治理缺口）

§2 声称六项决策"已确认"（分层扩展平台路线、受信内部扩展、随包交付并启停、`Change Proposal` 统一写入权、`Artifact` 流程、Cordis 借鉴边界），但仓库中不存在对应的 ADR、RFC 或 Research 记录其取舍依据。`Change Proposal`、`Artifact` 亦为本 PRD 首创概念，尚无 Spec/ADR 背书；AutoLISP (.lsp) 是仓库中唯一出现于本文的术语。按 ARCH-INT-001 §5.2："未采纳的架构设想进入 RFC 或 Research"、"关键方案取舍用 ADR"。

**建议**：将 §2 方向沉淀为 ADR（如 ADR-DM-005）或走 `integration/rfcs/` RFC，PRD `related` 引用之；若仍未正式裁决，措辞由"已确认决策"改为"拟定方向"。

### 2. 验收标准未覆盖全部 EXT 需求

AC-001~008 存在需求悬空：EXT-003（能力声明与最小授权）、EXT-007（任务持久化/重启后恢复）、EXT-012（按能力选择运行时）、EXT-013（设置隔离与升级迁移）无直接对应 AC。与 GUIDE-DM-001 G6"追踪矩阵"实践（每条 Spec 要求必须有验证）不一致。

**建议**：补 AC 或建立 EXT↔AC 映射表，建议条目示例：
- "测试扩展只能取得清单声明且宿主允许的能力，其余调用被拒"（对应 EXT-003）；
- "应用重启后，扩展任务能区分可恢复/可重试/已中断/需人工检查"（对应 EXT-007）；
- "运行时缺失或不匹配时，扩展在执行前得到明确诊断，不静默降级"（对应 EXT-012）；
- "扩展设置按 extension_id 隔离，升级迁移失败时保留旧数据"（对应 EXT-013）。

## 四、内容缺口（建议补充或显式推迟）

1. **同进程扩展资源治理未提**。SEC-004 承认同进程扩展仅受能力边界约束，但 CPU/内存/事件循环饥饿、宿主冻结风险无约束，也未列入非目标。建议补一条或显式声明为 Spec 议题。
2. **"一切能力皆可组合"缺乏操作性定义**。总体原则声称能力可组合，但无任何 EXT 定义扩展间互操作规则（如扩展 A 调用扩展 B 登记的能力）。建议补需求或放入非目标。
3. **AutoLISP 是全新执行面**。仓库唯一出现 AutoLISP 处即本文档；现有实现为固定 SCR + .NET Worker（ADR-DM-002/SPEC-DM-002）。将其列为作业可调用内容须在对应 Spec 前做独立安全设计，或注明"如引入须另行评估"，确保与"用户不可提交脚本"的安全叙事不冲突。
4. **§6.2 成功结果与 §14 验收并行表述**。尚可接受，但按 GUIDE-DM-001"一条要求只有一个权威来源"原则，建议明确 §6.2 是产品目标层、§14 是可核验验收层。
5. **§1"不规定实施顺序"与 §13 能力演进顺序存在张力**。正文已有自我辩护（"不是实施 Plan，不绑定版本或日期"），建议措辞改为"风险治理顺序"以免误读。
